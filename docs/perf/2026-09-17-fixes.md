## Task 18: 止まっている間は水深の canvas を再描画させない（spec 06 §5.2、計画で決めたこと 16）

- 対応: Task 10 の「止まっている間の再描画」の 2 秒の render の回数が 0 より大きい（120）。計画 `docs/superpowers/plans/2026-09-17-06-performance.md` Task 18
- 実装: `WaterOverlay.addLayers` の canvas ソースを `animate: true` から `animate: false` に変えた。`draw()` の `putImageData` の直後に新しい `uploadCanvasSource(source)` を呼び、`source.play()` の直後に `source.pause()` を呼ぶ。MapLibre 6.6.0 の `CanvasSource` は `play()` で `_playing` を立てて `triggerRepaint()` し（そのフレームで `hasTransition()` が真になり canvas を texture へ転送）、`pause()` は `_playing` の間に `prepare()`（texture.update）を呼んでから `_playing` を下ろす（`node_modules/maplibre-gl/dist/maplibre-gl-dev.mjs` 4601〜4609・4649 行）。`_playing` を立てたままにしないので、`animate: true` のときのような毎フレームの `triggerRepaint()` が止まる。play・pause は onAdd の load() で付くので、まだ読み込まれていないソース（`play` が無い）では何もしない
  - **spec と違えたところ**: spec 06 §5.2 は「止まっている間は pause、動いているときは play」という形を挙げているが、この Task では計画どおり「animate: false ＋ 描いたときだけ play()/pause() を 1 回呼ぶ」形にした（controller 裁定 C9）。理由: `CanvasSource.load()` は `animate` が真のときだけ `play()` を呼ぶ（`maplibre-gl-dev.mjs` 約 4614 行）。spec の字面どおりに `animate: true` のまま止まっているときだけ pause を呼ぶ形にすると、2D では地図が動いていない間の再描画は止まるが、**3D では水面（Custom Layer）がこの canvas ソースを直接使わず隠れているだけ**なので、animate: true が生む「地図全体を毎フレーム再描画させる」効果はそのまま残り、3D の間の隠れた 2D canvas の再描画（と、それに相乗りする地図全体の再描画）が止まらない。animate: false ＋ 描画時だけ play/pause の形なら、2D・3D どちらでも「描いたときだけ転送・再描画を 1 回頼む」に統一できる
- `MapController.ts` のコメント（21〜23 行、animate: true のせいで idle が二度と来ないという記述）は、animate: false にした今は古い。「レイヤー・ソースの追加/削除や setLayoutProperty は `Map._update()` が必ず `triggerRepaint()` を呼ぶので（`maplibre-gl-dev.mjs` 26113〜26118 行）、この関数が数える対象が変わった直後には必ず render が来る」という、実際に `data-overlay-layers`・`data-overlay-order` を成り立たせている理由に書き直した
- **R-d（render に相乗りする消費者の確認）**: animate: true をやめると、地図が本当に何も変わっていない間は render が来なくなる。`render` に乗って更新している印を洗い出し、それぞれが animate: true 由来の連続再描画に頼っていないか確かめた
  - `MapController.writeOverlayLayers`（`data-overlay-layers`・`data-visible-overlay-layers`）と Task 17 の `data-overlay-order` は同じ `render` リスナーから書く。これらが変わる操作（`addLayer`・`removeLayer`・`setLayoutProperty`・`setStyle`）はすべて MapLibre の `Map._update()` を経由し、`_update()` は無条件に `triggerRepaint()` を呼ぶ（上記 26113〜26118 行）。animate とは無関係に、変化の直後に render が 1 回来る。追加の `triggerRepaint()` は不要と判断した
  - `View3d` の印（`writeMarks` の `data-map-zoom`・`data-map-pitch`・`data-drawn-tile-zoom`）も同じ `render` リスナー（`onRender`）から書く。`mapZoom`・`mapPitch` はカメラの移動（`move`・`zoom` イベント。`Map` コンストラクタで `_update` を呼ぶよう配線済み）、`drawnTileZoom` は地形タイルの到着（ソースの `data` イベント。Map が `on("data", ... this._update(...))` で配線済み、`maplibre-gl-dev.mjs` 23325〜23327 行）で変わり、どちらも animate とは別の経路で `triggerRepaint()` を起こす
  - `View3d.requestBoundaryCheck` はもとから明示的に `map.triggerRepaint()` を呼んでいる（`View3d.ts` 370 行）ので変更不要
  - 以上により、この Task では追加の `triggerRepaint()` 呼び出しは不要と判断した（コードの変更はしていない）。判断の裏付けとして、E2E（重ね描きの並び・3D の切り替え・境界の判定・ベースマップの切り替え・コンテキスト喪失からの復帰を含む）を 2 回続けて回し、43 件とも成功することを確かめた（下記）
