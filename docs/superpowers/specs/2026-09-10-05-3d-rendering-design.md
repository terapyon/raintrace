## 1. 目的

範囲の地形と水面を 3D で表示し、垂直強調・水深の色分け・流れの矢印・視点の操作を提供する。これで base-spec §57 の PoC 完成条件がすべてそろう。

S の結論を受けたユーザーの裁定（2026-09-13）で、方式 A（MapLibre の 3D terrain ＋ 水面の Custom Layer）に決まった（RS-4、tech-spec §5.5）。§3 はどの方式でも変わらない部分、§4 は方式 A に固有の部分である。

## 2. スコープ

### 含む

- 地形の 3D 表示（方式 A。§4）
- 水面の 3D 表示と、水深の色分け（5cm 刻み）
- 垂直強調（1・2・5・10x）を地形と水面に同じ倍率で適用（base-spec §29）
- 水の流れの矢印の 3D 表示
- 3D での地点・セルの選択（クリック）
- 2D と 3D の切り替え（R05-1）
- WebGL のコンテキスト喪失からの復帰
- 本番のタイルの経路での fps の測り直しと調整（§4.4、R05-6）

### 含まない

- 建物などの構造物（base-spec §53.7）、WebGPU（tech-spec §1.1）
- 水面の高さに置く矢印の Custom Layer（§3.3。06 以降）

## 3. 方式によらない設計

### 3.1 水面（R05-2）

- 標高を `R32F` のテクスチャに一度だけアップロードし、水深を `R32F` のテクスチャに、新しいフレームが届くたびに `texSubImage2D` で更新する（N = 512 で 1MB。1000 m では 1031² で 4.25 MB）
- 格子のメッシュ（N × N の頂点、三角形 約 52 万枚）を一度だけ作り、頂点シェーダで `texelFetch` により高さを付ける: `高さ = (標高 + 水深) × 垂直強調`。標高はシミュレーションの標高（方式 A での置き方は §4.3）
- フラグメントシェーダで、水深 1cm 未満を捨て（base-spec §30）、水深を 5cm 刻みの色に対応させる。配色は 04 の 2D 表示と同じにする
- メッシュの形を毎フレーム作り直さないので、CPU の負担は 1MB のアップロードだけになる。S の実測（実 GPU・headless）では、水深のアップロードを含む render の CPU は 0.19〜0.22 ms で、0.3 ms 未満だった（S の報告 §4、Task 8）
- `texelFetch` を使うため、浮動小数点テクスチャの線形補間の拡張は要らない（WebGL2 の範囲で済む）

**行列**（S のすべての候補がこの形で描いた。S の報告 §5）:

| 項目 | 設計 |
|---|---|
| 頂点 | 格子の局所座標（列 + 0.5、行 + 0.5）だけを持つ。高さ（m）は頂点シェーダが付ける |
| モデル行列 | 局所座標からメルカトルへの換算（範囲の原点、セルの大きさ、m からメルカトルの単位への換算 `meterInMercatorCoordinateUnits`、垂直強調）を入れる |
| 投影 | 描くたびに `defaultProjectionData.mainMatrix` × モデル行列を JS の倍精度で掛け、Float32 にして渡す。メルカトル座標をそのまま float32 の頂点に入れると、約 1 セルで精度が尽きる。`modelViewProjectionMatrix` は頂点に使わない（x・y がワールドの画素で、float32 の精度が足りない） |
| Custom Layer | `renderingMode: '3d'`。three を使うので（§3.8）、描く前に `resetState` と viewport を設定する |

`mainMatrix` は絶対標高の行列で、シミュレーションの標高 × 倍率を高さとして描けば MapLibre の地形と同じ位置に来る（S の判定 (1): `map.project` との差は 16 通りすべてで最大 0.061 px）。

**z-fighting**: 水面を地形の後に描き、`polygonOffset(−1, −4)` を採る。平面の 1cm の膜で 8/8 ○（可視率の最小 0.9986、ちらつきの最大 0.0077%）。対策なしでは倍率 1 の z15〜z17 で落ちる（S の報告 §4、§10.3）。偏りは距離の 2 乗に比例し、z15 p0 で約 3 cm になる。遠景では、薄い尾根越しに向こうの水面を透けさせうる。

### 3.2 垂直強調

- 1・2・5・10x（base-spec §29）。表示だけに効き、計算には影響しない
- 地形と水面に必ず同じ倍率を掛ける。倍率の値は1か所（ストア）で持ち、両方がそれを読む

### 3.3 流れの矢印

symbol レイヤーで描く（裁定は要らない。レビュー役と合意）。

- 04 の `arrows`（frame の `[列, 行, 方位（度）, 大きさ]`）を MapLibre の symbol レイヤーで描き、**水面の Custom Layer の後に置く**（S の報告 §10.2）。矢印は MapLibre が地形に載せ、倍率に従う。水面の後に置けば、水深に関係なく水面の上に描かれる
- symbol は地表の高さに載るので、斜めの視点では水面の高さに置いた場合との視差が出る。視差は水深 × 倍率（渋谷 500 m の満水 4.65 m、倍率 10 で最大 約 47 m。S の `real-scene.md`）。池の上に矢印が浮いて見えるが、PoC では許す。水面の高さに置く Custom Layer は 06 以降
- **範囲 1000 m での間隔と密度**（04 の申し送り。1000 m では矢印が範囲を埋め、水が見えにくい）: 1 辺あたりの矢印の本数を、500 m の既定（間隔 10 m、1 辺 約 50 本）にそろえる。すなわち間隔を範囲の一辺に比例させ、1000 m の既定の間隔を 20 m にする。水の流れの矢印と地形の流向の矢印（04 で共通の間隔）の両方に効く。選べる間隔（今は 5・10・20 m）を範囲に応じてどう変えるかと最終の値は、05 の手動確認（1000 m）で決める
- spill point の印の数は窪地の表示の閾値（R02-3）で決まるので、この spec では扱わない

### 3.4 視点

- パン・ズーム・回転・pitch は MapLibre の標準の操作（base-spec §35）。シミュレーション中も動かせる
- 3D に切り替えたときは、pitch 60° で範囲全体が収まる視点に移る
- (c) の境界より粗い場合の扱いは §4.3

### 3.5 選択（クリック）

- 3D でも、04 のクリックの状態遷移（R04-1）をそのまま使う。違うのはクリック位置からセルを求める方法だけ（§4.1）

### 3.6 2D と 3D の切り替え（R05-1）

- パネルのスイッチで切り替える。2D では 04 の表示、3D ではこの spec の表示を使う
- 2D の表示は削除しない。3D の描画に問題があっても、シミュレーションの結果を確かめる手段として残す（tech-spec §5.5 の検証用ビュー）

3D での 04 の重ね描き:

| 04 の重ね描き | 3D での扱い |
|---|---|
| 標高の色分け・窪地（canvas） | そのまま表示する。MapLibre の地形は raster・canvas のレイヤーを地形に貼る（drape）ので、地形の上に載る |
| 水深（canvas、`WaterOverlay`） | 3D では切る。水面の Custom Layer と二重になるため。2D に戻したら表示する |
| 流れの矢印 | §3.3 |

- 3D のレイヤー（水面の Custom Layer、hillshade など）も `MapController.onRestyle` で足し直す。E2E で見るものは `data-overlay-layers` の一覧（04 の `TERRAIN_LAYER_IDS`・`WATER_LAYER_IDS`）に足す（04 の申し送り）

### 3.7 コンテキスト喪失

MapLibre 6.6.0 は、喪失（`_contextLost`）で painter とスタイルを破棄し、復帰（`_contextRestored`）で保存したスタイルを `setStyle(…, { diff: false })` で戻す。Custom Layer は戻さない（「cannot be restored after WebGL context loss. You will need to re-add it manually」と警告する）。したがって、復帰はテクスチャとメッシュを作り直すだけでは済まない。

| 対象 | 復帰の仕方 |
|---|---|
| 水面の Custom Layer（three の資源〈WebGLRenderer・テクスチャ・メッシュ〉を含む） | 新しいコンテキストで作り直し、04 の `MapController.onRestyle` の経路（§3.6 と同じ仕組み）で足し直す |
| hillshade と 04 の重ね描き | 同じ `onRestyle` の経路で足し直す。保存したスタイルに残っているものと二重にならないようにする |
| raster-dem のソースと `setTerrain` の地形 | 保存したスタイルに入るので、MapLibre が戻す。`addProtocol` の登録は地図の外にあり、喪失の影響を受けない。05 で確かめる（§5 の手動） |

- 今の `MapController` は、`setBasemap` の後の `style.load` でだけ `onRestyle` の購読者を呼ぶ。復帰の `setStyle` の後でも呼ぶように広げる
- S では確かめていない（S の報告 §11 (d)）

### 3.8 three の置き場所と読み込み（R05-5）

- 水面は Three.js で描く（2026-09-13 の裁定。ユーザーの言葉: 「後読みなら何の問題もない」）
- three を import してよいのは 3D の描画のモジュール（tech-spec §4.1 の `src/renderer/`）だけにする。ほかの層は `src/renderer/` を通して使う（tech-spec §4.2 の依存の向きのまま）
- `src/renderer/` と three は動的 import で読み、初期ロードのチャンクに入れない（tech-spec §14.2。初期ロード 425.1 KB は変わらず、総量は約 692.0 KB、上限 1.2 MB）。`vite.config.ts` の `ui` のチャンクの一覧に three を吸い込まない（04 の申し送り）
- 読み込むのは 3D に切り替えたとき（tech-spec §14.2）。具体的な検査（dependency-cruiser の規則、チャンクの検査）は計画で決める

## 4. 方式 A の設計（S の結論、2026-09-13 の裁定）

S の報告 §8 の推奨どおり、方式 A を採る（RS-4）。A'（水面の高さを `queryTerrainElevation` で MapLibre の地形に合わせる）は採らない。高さの取り直しが速い経路でも 123〜156 ms かかり（tech-spec §14.1 の上限は 50 ms）、表示される水面の高さがシミュレーションの標高と最大 0.024 m × 倍率 食い違う（S の報告 §8 の規則 3）。

### 4.1 要点

| 項目 | 設計 | 根拠（S の報告） |
|---|---|---|
| 地形 | `addProtocol` で Terrarium のタイルを作り、`setTerrain` で表示する（§4.2） | §8 の規則 2、§10.1 |
| 垂直強調 | `setTerrain({ exaggeration })` と水面のシェーダに同じ値（§3.2 のストアの値） | §4 の合格基準 2 |
| 水面の高さ | シミュレーションの標高（A）＋ 水深。弦の沈み込みの扱いは §4.3（R05-4） | §8 の規則 3、§10.1 の 1 |
| z-fighting | 水面を地形の後に描き、`polygonOffset(−1, −4)`（§3.1） | §4、§10.3 |
| 流れの矢印 | symbol レイヤーを水面の後に置く（§3.3） | §10.2 |
| クリックからセルへ | MapLibre の `unproject`（地形を考慮する）で緯度経度を求め、セルに変換する。S では試していないので、E2E と手動で確かめる（§5） | §11 (d) |
| 範囲の境界 | 標高 × 倍率の段差は無い。範囲の中と外で DEM の出所が変わる境目は §4.2 | §4 の継ぎ目、§10.1 の 4 |

### 4.2 地形のタイル

| 項目 | 設計 |
|---|---|
| 範囲の中 | 描かれるすべてのズームで、02 のグリッド（シミュレーションと同じデータ。メインスレッドでは `SimulationClient.terrain` の複製）から Terrarium のタイルを作る。こうすると、地形とシミュレーションの標高の差は弦の高さ（と縮小でなめらかになる分）だけになる（S の報告 §10.1 の 4、§11 (b)） |
| 範囲の外 | GSI の標高タイル（ズーム Z−1）を Terrarium に変換する。範囲の中と外の境目の扱いは計画で決め、手動で確かめる（§5） |
| GSI に無いズーム | 例: z16。隣のズームから作る（S の報告 §10.1 の 3） |
| `tileSize` | raster-dem に `tileSize: 256` を明示する。256px の DEM で既定の 512 のままにすると、頂点間隔が 2 倍、弦の高さが 4 倍になる（S の報告 §10.1 の 2） |
| 画素の値の置き方 | 角の規約: MapLibre（`DEMData.sampleBilinear`）は画素の値を「タイルの角からの連続座標（頂点）の高さ」として読むので、画素には角の位置の高さを書く。セルの中心の値を書くと、地形が最大 1 画素ずれる（S の報告 §5 の「地形の生成の修正」） |
| 無効セル | 0 m として書かない。0 m にすると周りの有効な標高との間に穴を掘り、倍率の分だけ深くなる。近くの有効セルの値で埋めるなど、書き方は計画で決める。地形の側で埋めると、2D の重ね描きでは無効セルは穴のまま、3D の地形では地面になる。この違いは許す。水は無効セルで水深 0 なので、1cm 未満を捨てる規則（§3.1）で描かれず、影響しない。範囲の外の GSI の無効値も同じ。実データの針状のノイズは、S で無効画素を埋めても変わらず、原因が未確定（S の報告 §11 (f)）なので、手動で確かめる（§5） |
| 作る場所とコスト | `addProtocol` はメインスレッドで呼ばれる。タイルごとの変換（角の規約の双線形を含む）のコストを測り、重ければ Worker に移す。S はメインスレッドで ImageBitmap を作り、その仕事量を測っていない。§4.4 の測り直しで扱う |
| hillshade | S は同じ DEM の hillshade を重ねて起伏を見せた。本番の 3D で要るか（淡色地図では無いと起伏が読みにくい）、写真の地図では要らないかを決める。fps への影響は §4.4 で測る |

### 4.3 水面の置き方（R05-4）

曲面では、描かれる地形タイルのメッシュが弦の高さぶん水面より上に出る。MapLibre の地形はタイルごとに 128 × 128 の格子で頂点を置き、頂点の間を線形に補間するためである。弦の高さ（S の報告 §10.1 の表。渋谷の緯度、S のすり鉢と同じ曲がり方の場合）:

| 描かれる地形タイルのズーム | 頂点間隔 | 弦の高さ |
|---:|---:|---:|
| 14 | 15.5 m | 約 10 cm |
| 15 | 7.76 m | 約 2.5 cm（直接の計算で最大 2.46 cm） |
| 16 | 3.88 m | 約 0.6 cm |
| 17 | 1.94 m | 約 0.15 cm |
| 18 | 0.97 m | 約 0.04 cm |

- 描かれるタイル 15 の 2.46 cm は、p0 の描画では polygonOffset の偏り（約 3 cm）が覆う。斜め視点（すり鉢の下のタイル 14〜18、最悪 0.0998 m）は未確定
- 斜め視点では、画面の中心が細かいタイルでも、遠景はタイル 14〜15 で描かれる。遠景の沈み込みは最大 約 10 cm になりうる
- 実データでは、弦の高さは場所ごとの曲がり方に従う

選択肢（S の報告 §10.1 の 1）と選ぶ基準:

| 基準 | (a) `max(sim, meshHeightAt(描かれるタイルのズーム)) + 水深` | (b) ズームに応じたかさ上げ・深度のバイアス | (c) 粗いズームは 2D（3D は描かれるタイルのズームが境界以上のときだけ） |
|---|---|---|---|
| 実装のコスト | 高い。場所ごとに描かれるタイルのズームが要り（`getRenderableTiles`）、MapLibre のメッシュの高さ（`meshHeightAt`）を複製して版に追従する | 中。ズームごとの係数を持ち、近くと遠くの両方で確かめる | 低い。2D は 04 の表示（R05-1）をそのまま使う。画面の中心で描かれるタイルのズームを求める部分は要る |
| 水面の高さの、シミュレーションの標高からのずれ | 弦の分だけ上にずれる（描かれるタイル 15 で最大 2.46 cm × 倍率。A' の食い違い 0.024 m と同じ大きさ） | かさ上げなら、その分だけずれる。深度のバイアスなら位置はずれない | ずれない（シミュレーションの標高 ＋ 水深） |
| 斜め視点の遠景の沈み込み（タイル 14〜15、最大 約 10 cm） | 描かれるタイルごとに持ち上げるので直る | 1 つの値で近くと遠くの両方を覆うのは難しい | 残る。偏りが遠くで覆うかもしれないが未検証。§6 の手動確認で見る |
| polygonOffset の偏り（距離の 2 乗に比例） | 偏りに頼らない。係数は (−1, −4) のまま | 近くの弦を覆うほど係数を強めると、遠くの水面が薄い尾根越しに透ける（S の報告 §10.3） | 係数は (−1, −4) のまま。境界以上では、弦（約 0.6 cm 以下）を偏りが覆う |

**推奨: PoC の既定は (c)**。実装が最も安く、水面の高さがシミュレーションの標高からずれない。(a) は場所ごとの描かれるタイルのズームが要って重いので、06 以降の候補として残す。05 の中で上の基準で決める。

**境界のズームは 1 つの定数で持つ**。(c) で 2D に切り替える境界と、§4.4 の fps の調整で粗いズームを 2D にする境界は、同じ定数を使う。沈み込みと fps で別々の閾値を持つと、後で食い違う。定数は描かれる地形タイルのズームで定義する。根拠は上の弦の高さの表で、描かれるタイル 16 以上なら弦は約 0.6 cm 以下になる。値は、計画・実装で実測して決める。有力なのは 15（下の (ii)）。S では地図・タイル・DEM のズームの取り違えで 3 回の直しが入ったので、描かれるタイルのズームは実測で確かめる（S の報告 §10.1 の 5）。境界の判定は、画面の中心で描かれている地形タイルのズームの実測で行う。2D に落ちた後は地形が無く実測できないので、3D に戻す判定だけは pitch つきの見込み（画面の中心で描かれるタイルのズームの予測）で行い、見込みが**境界 + 0.5 以上**になったら 3D に戻す（行き来のたびに地形と水面を作り直さないための余裕。戻した直後の描画で実測を確かめ直す。2026-09-16、実装で決めた値を追記）。

**(c) と、範囲の全体を収める視点（§3.4）**: MapLibre の地図のズームは、ズーム 0 で世界が 512 px。地形が有効な間、MapLibre はタイルごとに可変のズームで描く。描かれる地形タイルのズームは、pitch 0 では地図のズームと同じだが（raster-dem が `tileSize: 256` のとき）、pitch 60 では 1 段、pitch 85 では 1〜2 段粗い（S の `bowl-film-mesh.md`）。確かめ（pitch 0）: ズーム 15 では 1.94 m/px、タイルの幅は 993.7 m で、993.7 ÷ 128 = 7.76 m が S の頂点間隔と一致する。渋谷の緯度・pitch 0 で、範囲が画面の幅に収まる地図のズーム（下の表は pitch 0 の値）:

| 範囲 | 画面の幅 400 px | 600 px | 900 px |
|---|---:|---:|---:|
| 500 m | 約 15.6 | 約 16.2 | 約 16.8 |
| 1000 m | 約 14.6 | 約 15.2 | 約 15.8 |

pitch 60 では、画面の中心でも描かれるタイルが 1 段粗くなり、上半分はさらに粗くなる。したがって、範囲の全体を収める地図のズームが境界以上でも、描かれるタイルは境界より粗くなりうる。境界を 16 にすると、1000 m の全体の視点は幅 900 px まで常に 2D に落ち、500 m の全体の視点もスマートフォンの幅では 2D に落ちる。計画で次から選ぶ（組み合わせてよい）:

- (i) 3D に切り替えたときは、範囲の全体ではなく中心寄り（範囲の半分ほど）を収める視点にする
- (ii) 境界を 15 にする（有力）。z15 の弦 2.46 cm は、p0 の描画では polygonOffset の偏り（約 3 cm）が覆い 8/8 ○。未確定なのは斜め視点だけなので、§6 の手動確認で決める
- (iii) 2D に落ちることを受け入れ、2D に落ちたことを表示する

斜め視点で 15 が通らなければ（境界が 16 になり、1000 m の全体の視点は 900 px 以下のどの幅でも 2D になる）、その時点でユーザーの裁定に上げる（3D を近いズームに限るか、遠景の沈み込みを PoC で許すか）。

### 4.4 fps（合格基準 3、R05-6）

S の参考値（実 GPU・headless、GTX 1080 Ti、60Hz が上限。実データ、水深を毎フレーム更新。S の報告 §4、§8 の規則 1）:

| 視点 | A | 地形のみの A（水面なし） |
|---|---|---|
| z17 ×5 p60 | 58.0 fps、長いフレーム 291 間隔のうち 2（0.7%） | 58.0 fps、0.7% |
| z16 ×10 p85 | 56.8 fps、285 のうち 6（2.1%） | 56.2 fps、283 のうち 7（2.5%） |

- z16 ×10 p85 は、S の D15（平均 57 fps 以上、かつ長いフレーム 1% 以下。長いフレームはそのランの中央値の 2.5 倍を超えた間隔）の両方を外す
- 地形のみでも同じなので、不足は地形の経路にある。水面が足す render の CPU は約 0.2 ms
- 原因は切り分けていない: (i) `addProtocol` の中でメインスレッドで行う Terrarium への変換、(ii) 重ねている hillshade、(iii) MapLibre の地形の描画そのもの（S の報告 §11 (e)）

**裁定（2026-09-13）**: 基準 3 を外しても A を保つ（「Aでよい」）。B 系には移らない。05 の中で、本番のタイルの経路で fps を測り直して改善する。

**測り直し（05 の最初のタスク）**: 本番のタイルの経路（§4.2 のタイルの生成）で、S と同じ 2 視点・同じ指標（平均 fps、長いフレーム、D15）を測る。開発機の実 GPU での手動の計測と、headless の参考値の両方を取る。

| 変える条件 | 値 |
|---|---|
| タイルの変換・生成を行う場所 | メインスレッド（`addProtocol` の中）／Worker／範囲の外の GSI タイルを raster-dem の `encoding: 'custom'` で直接読む（変換を省く。負の標高と無効値 2^23 で崩れるので、使えるかをまず確かめる。S の報告 §11 (a)） |
| hillshade | あり／なし |
| 水面 | あり／なし（地形のみの基準） |
| 範囲 | 500 m／1000 m。S は 500 m だけを測った（N ≈ 515、水深のテクスチャ 約 1 MB）。1000 m は 1031² で、frame と水深のテクスチャが 4.25 MB になり、毎フレームの `texSubImage2D` が 4 倍になる。1000 m の読み込みの終わりには 123 ms のタスクもある（tech-spec §14.2） |

長いフレームが決まったタイミングで繰り返し起きることの原因も、あわせて見る（S の報告 §11 (e)）。

**結果から選ぶ調整**（05 の中で決め、計画と PR に記録する）:

| 調整 | 内容 | 代償 |
|---|---|---|
| タイルの生成をメインスレッドから外す | Worker に移す。範囲の外は `encoding: 'custom'` も候補 | 範囲の中の生成には、02 のグリッドの受け渡しが要る |
| hillshade を外す | 常に外す、または写真の地図でだけ外す（§4.2） | 淡色地図では起伏が読みにくい |
| 粗いズームを 2D にする | 境界は §4.3 と同じ 1 つの定数 | 境界より粗いズームでは 3D が見えない |
| 地形を描く範囲を狭める | 範囲とその周りだけを 3D の地形にする | 範囲の外との境目に継ぎ目が戻る |

これらでも 60 fps に届かない条件が残れば、その条件と値を記録して 06（性能）に引き継ぐ。

> 裁定（2026-09-10）: R05-1〜R05-3 はすべて推奨どおり承認。
