## 1. 目的

範囲の地形と水面を 3D で表示し、垂直強調・水深の色分け・流れの矢印・視点の操作を提供する。これで base-spec §57 の PoC 完成条件がすべてそろう。

この spec は、S の結論によって地形の描き方が変わる。そのため、どの方式でも変わらない部分（§3）を先に確定させ、方式によって変わる部分（§4）は候補ごとに書いておく。S の完了後に §4 を1つに絞って改訂する。

## 2. スコープ

### 含む

- 地形の 3D 表示（方式は S で決まる）
- 水面の 3D 表示と、水深の色分け（5cm 刻み）
- 垂直強調（1・2・5・10x）を地形と水面に同じ倍率で適用（base-spec §29）
- 水の流れの矢印の 3D 表示
- 3D での地点・セルの選択（クリック）
- 2D と 3D の切り替え（R05-1）
- WebGL のコンテキスト喪失からの復帰

### 含まない

- 建物などの構造物（base-spec §53.7）、WebGPU（tech-spec §1.1）

## 3. 方式によらない設計

### 3.1 水面（R05-2）

- 標高を `R32F` のテクスチャに一度だけアップロードし、水深を `R32F` のテクスチャに、新しいフレームが届くたびに `texSubImage2D` で更新する（N = 512 で 1MB）
- 格子のメッシュ（N × N の頂点、三角形 約 52 万枚）を一度だけ作り、頂点シェーダで `texelFetch` により高さを付ける: `高さ = (標高 + 水深) × 垂直強調`
- フラグメントシェーダで、水深 1cm 未満を捨て（base-spec §30）、水深を 5cm 刻みの色に対応させる。配色は 04 の 2D 表示と同じにする
- メッシュの形を毎フレーム作り直さないので、CPU の負担は 1MB のアップロードだけになる
- `texelFetch` を使うため、浮動小数点テクスチャの線形補間の拡張は要らない（WebGL2 の範囲で済む）
- 水面と地形が 1cm 差で重なる箇所の z-fighting には、S で有効だった対策を採る

### 3.2 垂直強調

- 1・2・5・10x（base-spec §29）。表示だけに効き、計算には影響しない
- 地形と水面に必ず同じ倍率を掛ける。倍率の値は1か所（ストア）で持ち、両方がそれを読む

### 3.3 流れの矢印

- 04 の `arrows` を使い、インスタンス描画した矢印を水面の高さに置く。方式 A の場合は、MapLibre の symbol レイヤーを地形に載せる方法も S で比べる

### 3.4 視点

- パン・ズーム・回転・pitch は MapLibre の標準の操作（base-spec §35）。シミュレーション中も動かせる
- 3D に切り替えたときは、pitch 60° で範囲全体が収まる視点に移る

### 3.5 選択（クリック）

- 3D でも、04 のクリックの状態遷移（R04-1）をそのまま使う。違うのはクリック位置からセルを求める方法だけ（§4）

### 3.6 2D と 3D の切り替え（R05-1）

- パネルのスイッチで切り替える。2D では 04 の表示、3D ではこの spec の表示を使う
- 2D の表示は削除しない。3D の描画に問題があっても、シミュレーションの結果を確かめる手段として残す（tech-spec §5.5 の検証用ビュー）

### 3.7 コンテキスト喪失

- `webglcontextlost` で描画を止め、`webglcontextrestored` でテクスチャとメッシュを作り直す

## 4. 方式によって変わる部分（S の結論で1つに絞る）

| 項目 | 方式 A（MapLibre の地形） | 方式 B（範囲内は自前の地形） |
|---|---|---|
| 地形 | `addProtocol` で GSI の標高 PNG を Terrarium 形式に変換し、`setTerrain` で表示。無効値は 0m として描く | 範囲の標高テクスチャから地形のメッシュを描き、ベースマップのタイルを canvas に合成してテクスチャにする。範囲の境界には縁（スカート）を付けて継ぎ目を隠す |
| 垂直強調 | `setTerrain({ exaggeration })` と、水面のシェーダに同じ値 | 地形と水面のシェーダに同じ値 |
| 水面の高さ | シミュレーションの標高を使う（A）、または MapLibre の地形に合わせる（A'） | 地形と同じ標高テクスチャ |
| クリックからセルへ | MapLibre の `unproject`（地形を考慮する）で緯度経度を求め、セルに変換 | 標高の格子に対するレイの交差を CPU で求める |

## 5. テスト

| 種類 | 内容 |
|---|---|
| ユニット | メッシュの頂点番号の生成、テクスチャへの詰め方、垂直強調の変換、（方式 B なら）合成した高さの場に対するレイの交差 |
| E2E | 3D に切り替えてもコンソールにエラーが出ない。3D でクリックするとセル情報が開く。2D に戻せる |
| 手動 | S の合格基準の組み合わせ（垂直強調 × pitch × ズーム）を実アプリで確かめ、スクリーンショットを PR に記録。Firefox と Safari でも確かめる |

描画結果の画素の比較は行わない（tech-spec §11.4）。

## 6. 完了条件

1. base-spec §57 #4・#9 を満たす（これで PoC 完成条件がすべてそろう）
2. S の合格基準を実アプリで満たす
3. §5 のテストが成功し、手動確認を記録している

## 7. 裁定が必要な論点

| ID | 論点 | 推奨 | 理由 |
|---|---|---|---|
| R05-1 | 2D 表示の扱い | 3D と切り替えられる常設のモードとして残す | 3D の描画の問題とシミュレーションの問題を切り分けられる。低性能の機器での代わりの表示にもなる |
| R05-2 | 水面の描画方式 | §3.1 のとおり（テクスチャと頂点シェーダ） | 毎フレームの CPU の仕事がアップロードだけになり、60fps の目標に最も近い |
| R05-3 | この spec の確定の仕方 | S の結論を受けて §4 を改訂し、再レビューしてから実装する | 方式が決まらないまま実装計画を立てても、半分が無駄になる |
