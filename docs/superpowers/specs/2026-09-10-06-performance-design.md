# Spec 06: 性能

- Status: Draft（レビュー待ち）
- 日付: 2026-09-10
- 対応: base-spec §22〜§26、§55 Phase 5、§63、tech-spec §6.3・§8.4・§14
- 依存: 04、05

---

## 1. 目的

tech-spec §14 の性能目標を実際のアプリで測り、条件付きの最適化（tech-spec §6.3 の WASM、§8.4 の IndexedDB など）を行うかどうかを判断する。

**この spec の成果物は計測の仕組みと判断であり、最適化そのものではない。** 基準を超えた項目についてだけ、個別の最適化の spec を別に起こす（tech-spec §2 原則4「速度は測ってから最適化する」）。

## 2. スコープ

### 含む

- 開発用の計測表示（オーバーレイ）
- 再現できるベンチマークのシナリオと、その実行手順
- 計測結果の記録
- 基準との比較と、最適化の要否の判断
- 1000m 四方（約 100 万セル）で実用になるかの確認（base-spec §8）

### 含まない

- 最適化の実装（基準を超えた場合に別の spec で行う）

## 3. 計測表示

`?debug=1` を付けて開いたときだけ、画面の隅に次を出す（tech-spec §14.1「開発モードで統計を表示」）。本番のビルドにも含めるが、既定では表示しない。

| 項目 | 取り方 |
|---|---|
| 1 step の所要時間（中央値・p95） | Worker 内で `performance.now()`。直近 300 step の値から求める |
| 実際の step 数／秒 | Worker 内で数える |
| 描画の fps | メインスレッドの `requestAnimationFrame` |
| 長いタスク（50ms 超） | `PerformanceObserver` の `longtask` |
| 質量誤差 | 03 の `StepStats.massError` |
| 平衡までの step 数と時間 | `settled` になった時点の値 |

## 4. ベンチマーク

### 4.1 シナリオ

| 地点（R06-1） | 範囲 | 降雨 |
|---|---|---|
| 平坦な市街地 | 500m、1000m | 半径 10m・100mm、半径 100m・100mm |
| 谷のある斜面 | 同上 | 同上 |
| 沿岸（無効セルを含む） | 同上 | 同上 |

- 再現できるよう、3 地点の DEM タイルを `tests/perf/fixtures/` に保存して使う（出典を README に記す）
- 3D の有無で2通り測る
- 平衡までの時間は、1x と「最速」（R04-5）の両方で測る

### 4.2 実行方法

- **step の所要時間**は CPU だけで決まるので、Playwright からヘッドレスの Chromium で自動計測できる（`pnpm perf`）
- **fps と長いタスク**は GPU に左右されるので、ヘッドレス（ソフトウェア描画）では意味を持たない。開発機の実ブラウザで手動で測る
- 結果は `docs/perf/<日付>.md` に、機器の仕様とともに記録する

## 5. 判断

| 指標 | 基準 | 超えた場合の対応 |
|---|---|---|
| 1 step の中央値・p95 | 8ms・16ms（tech-spec §6.3） | まず安価な改善（16 × 16 セルのブロック単位の走査範囲など。03 §3.5）を試し、それでも超えれば Rust WASM の spec（tech-spec §6.4） |
| 平衡までの時間 | R06-3（池の幅で判断） | 03 §4.1 のとおり、(b) 静的な fill-spill-merge 法を本命、(a) virtual pipe モデルを次点として spec を起こす |
| 地図操作の fps | 60fps（シミュレーション中も） | どこで時間を使っているかを調べる。2D の水深の着色なら GPU に移す。3D ならアップロードの頻度を見直す |
| メインスレッドの最長ブロック | 50ms | 原因の処理を Worker へ移すか分割する |
| 地点のクリックから表示まで | 3 秒 | DEM の再取得が主因なら IndexedDB のキャッシュ（tech-spec §8.4）。そうでなければ取得の並列度やデコードを見直す |
| バンドル | tech-spec §14.2 の予算 | チャンクの分け方を見直す |
| 1000m 四方 | 上の基準をすべて満たすか | 満たさなければ、1000m の選択肢を外すか、注意を表示する |

## 6. 完了条件

1. §4 のすべてのシナリオについて、計測結果を記録している
2. §5 の各指標について、基準内か、超えていて対応の spec を起こしたかが決まっている
3. tech-spec §14 に、実測した基準値を書き込んでいる

## 7. 裁定が必要な論点

| ID | 論点 | 推奨 | 理由 |
|---|---|---|---|
| R06-1 | ベンチマークの地点 | 02 の手動確認と同じ 3 地点（R02-7） | 見た目の妥当性を確かめた地点で性能も測れば、比較しやすい |
| R06-2 | 性能を CI の必須ゲートにするか | しない。傾向を見るための任意のジョブ（ヘッドレスでの step の所要時間のみ）は置いてよい | CI の実行環境は性能がばらつくので、必須ゲートにすると関係のない PR が落ちる |
| R06-3 | 平衡までの時間の目標 | 池の幅で決める。幅 30 セル程度の池（半径 10m・100mm 相当）は 1x で 60 秒以内。幅 100 セル規模の池（半径 100m・100mm 相当）は「最速」で 5 分以内 | 平衡までの時間を決めるのは、降雨の半径ではなく、できる池の幅である（03 §4.1）。後者は未達の公算が高く、その場合は (b) 静的な fill-spill-merge 法の spec を起こす。値は、利用者が結果を待てる長さとして置いた暫定のもの |
