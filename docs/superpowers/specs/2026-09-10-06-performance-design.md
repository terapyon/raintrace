## 1. 目的

tech-spec §14 の性能目標を実際のアプリで測り、**原因を切り分け、安価で局所的な改善は 06 の中で直す**（R06-4）。条件付きの最適化（tech-spec §6.3 の WASM、§8.4 の IndexedDB など）を行うかどうかを判断する。

- 直すのは「安価」な項目だけで、**直す前と後を同じ条件で測る**。安価 = 新しい依存を足さない、新しい Worker を足さない、`SimulationEngine` とメッセージ（`src/shared/protocol.ts`）の形を変えない
- 構造に関わるもの（Rust WASM〈tech-spec §6.4〉、fill-spill-merge〈03 §4.1〉、遠景の LOD、IndexedDB〈tech-spec §8.4〉）は、06 の判断が要ると決めた場合に別の spec を起こす（tech-spec §2 原則4「速度は測ってから最適化する」）

## 3. 計測の道具（R06-5）

**計測表示は計測用のビルド（`pnpm build:perf`）にだけ入れ、本番のビルドには入れない**（R06-5。改訂前の「本番のビルドにも含める」を置き換える）。05 の不変条件（通常のビルドでは `__RAINTRACE_PERF__` が false になり、`src/main.tsx` の計測用のフックの分岐ごと消える）を保つ。

新しい仕組みは作らず、05 の道具を広げる: URL の読み取りは `perfParams`、画面の左上の JSON と `<html>` の `data-*` の結果は `perfHook`、フレームの計測は `fpsProbe`・`fpsStats`、自動の実行は `tests/perf/`（`playwright.perf.config.ts`）。

| 項目 | 取り方 | 状態 |
|---|---|---|
| 1 step の所要時間（中央値・p95） | Worker 内。`PlaybackScheduler` が step のたびにすでに呼んでいる `ports.now()` の差から求め、直近 300 step を持つ。タイマーの呼び出し回数を増やさない | **新規** |
| 実際の step 数／秒 | `PlaybackScheduler` の 1 秒の窓（frame の `stepsPerSecond`） | 既存 |
| 描画の fps | `fpsProbe`（1 秒の空回しの後の rAF の間隔）と `fpsStats`（D15。§5） | 既存。ヒストグラムの g2 もすでに結果に出ている（`fpsStats.ts` の `gapHistogram`、`fps.perf.ts` の表の g1/g2 列） |
| 長いタスク（50 ms 超） | `PerformanceObserver` の `longtask` を `perfHook` に足す（04 は使い捨てのスクリプトで仕込んだ） | **新規** |
| 質量誤差 | frame の `stats.massError`（03 §3.10） | 既存。表示だけ足す |
| 平衡までの step 数と時間 | `settled` になった時点の step と、開始からの `performance.now()` の差 | **新規**（04 は手で測った） |
| クリックから 2D の地形の表示まで | 地点の確定から地形のレイヤーが出るまで | **新規** |
| 3D を押してから最初の 3D のフレームまで | three の読み込み・3D の準備・水面のメッシュの作成・タイルが揃うまでを分けて。準備と作成は `onPrepareTime`・`onWaterBuildTime` が既存 | **一部新規** |
| 矢印を止める（`arrows=0`） | `perfParams` の項目。§5.1 の切り分け | **新規** |
| 水深テクスチャの更新の間引き（`depthEvery=N`） | `perfParams` の項目。N フレームに 1 回だけ転送する。§5.1 の切り分け | **新規** |
| 可視率・ちらつき率（`probe=water`） | 水面を深度テストなしと ありで描いて画素を数える。bearing を ±0.002° 揺らした 2 フレームを比べる。水面のシェーダの計測用の uniform 1 つと `perfHook` の分岐 1 つ（R06-7、M5） | **新規** |

- 1 step の所要時間を Worker からメインへ渡す方法は計画で決める。通常のビルドのメッセージの形と挙動は変えない（M1 の完了時に通常のビルドに計測のコードが入っていないことを確かめ直す）。型に手を入れる必要が出たら、計画のレビューに上げる
- `fps.perf.ts` の出力先は引数で渡す（既定は 05 の `.handoff/05-fps/` のまま。M0）

## 4. ベンチマーク

### 4.1 シナリオ

| 地点（R06-1、R02-7 で選んだ 3 地点） | 範囲 | 降雨 |
|---|---|---|
| 足立区 綾瀬駅付近（平坦な市街地） | 500 m、1000 m | 半径 10 m・100 mm、半径 100 m・100 mm、全面を濡らす雨 |
| 渋谷駅付近（谷のある斜面） | 同上 | 同上 |
| 横浜 みなとみらい（沿岸。無効セルを含む） | 同上 | 同上 |

- **全面を濡らす雨**: 半径を範囲の半分（R04-6 の上限）にする。濡れたセルの外接矩形が範囲全体になり、tech-spec §6.3 の走査の最悪の形になる。§6.3 を都合のよい条件だけで判断しないために、意図して入れる。雨量は計画で決める
- 3D の有無で 2 通り測る（step の所要時間・長いタスク・fps）
- **平衡までの時間は「最速」（R04-5）で測る**。1x は step 数 ÷ 60 で報告するが、目標にはしない（R06-6）。2 分で平衡に届かない雨は、打ち切りの上限を計画で決め、届かなかったことと、その時点の step 数を記録する
- fps は 05 の 4 視点（500 m・1000 m × z17 ×5 p60・z16 ×10 p85）× 地形のみ・水面ありを、3 地点で測る（05 は渋谷だけ）
- **DEM の用意**: CPU で決まる計測（step の所要時間・平衡）は、毎回同じ DEM で回す。Playwright の `context.route` で固定のタイル（フィクスチャ）を返し、アプリの取得の経路は変えない（§4.2）。DEM の取得は Worker の中で行うので、`page.route` では捕まらない。E2E の `routeGsi`（`tests/e2e/support/gsi.ts`）と同じく browser context で差し替える。**タイルの組が小さければリポジトリに置き、大きければ SHA-256 で固定した取得のスクリプトにする。どちらにするかは計画で決める**（`context.route` が返すフィクスチャの保存方法だけの問題になる）。出典は `tests/fixtures/gsi/README.md` と同じ形で記す。fps とクリックから表示までは、05 と同じく地理院に実際に接続する（本番のタイルの経路）

### 4.2 実行方法

- **自動**: `pnpm build:perf` の後に `pnpm perf:fps`（`playwright.perf.config.ts`。ポート 4175、実 GPU の headless Chrome〈`--use-gl=angle --use-angle=gl-egl`〉、workers 1）。組は `RAINTRACE_FPS_SET`・`RAINTRACE_FPS_REPEAT` で選び、新しい設定のファイルは作らない。05 は実 GPU の headless で fps を測れることを示した（改訂前の「ヘッドレスでは意味を持たない」は当たらない）
  - 限界: rAF が 60 Hz に刻まれるので、60.0 fps の天井に張り付いた条件は余裕を読めない（05 の 8 条件のうち 6 条件）。vsync を外す起動の引数（例: `--disable-gpu-vsync --disable-frame-rate-limit`）が ANGLE の gl-egl で効くかは**未検証**で、M3 で試す
  - GPU の時間（`EXT_disjoint_timer_query_webgl2`）はこの機械の Chrome で使えるか**未検証**。使える前提で計画しない
- **自動化（1 step の所要時間・平衡までの時間）**: `perfHook` に `probe=steps` を足す。降雨を開始し、`settled` になるか打ち切りの上限に達するまで待って、1 step の所要時間の統計（中央値・p95）・step 数・経過時間を JSON に書く。実行するファイルは `tests/perf/` に 1 つ足し、既存の `playwright.perf.config.ts` をそのまま使う（実 GPU の起動引数は CPU の計測を妨げない）。DEM は §4.1 のとおり `context.route` で固定のタイルを返し、アプリは変えない
- **手動（実 GPU、1 回）**: ユーザーが手で行う。**05 の手動確認の項目 9（fps の 8 個の URL）を含め**（R06-8）、§5.1 の切り分けの URL と、§3 の新しい計測（g2・長いタスク・step の所要時間）もこの回で取る
  - 機器の仕様を記録する: OS、CPU とコア数、GPU、`chrome://gpu` の GL_RENDERER、Chrome の版、画面のリフレッシュレート、ウィンドウの大きさ
  - 水面ありの計測では Worker が「最速」で 1 コアを使い続ける。05 の headless は 32 コアの機械なので競合しないが、コアの少ない機械では結果が変わりうる
- **基準の機械**: 「最速」の 60 秒・5 分の目標（§5）は CPU に依存するため、基準は自動化を回す開発機（05 の headless の実測をとった機械と同じ。仕様は `docs/perf/<日付>.md` に機器の仕様とともに記録する）とする。ユーザーの手動の計測は参考値であり、基準の判定には使わない
- **記録**: 要約は `docs/perf/<日付>.md` に機器の仕様とともにコミットする。生の JSON（`deltas` を含む）は大きいので gitignore の `.handoff/` に置く

### 5.1 51 fps の切り分け（M3）

条件は 05 と同じ（1000 m・z16 ×10 p85、`fallback=0`、渋谷、新しい context）。同じ視点で次を変えて比べる。

| 変える条件 | 見るもの |
|---|---|
| `depthEvery=N`（N = 1・2・4） | 転送が主因なら N を上げたぶん fps が戻る。描画が主因ならほとんど変わらない（レビュー役の提案） |
| 止めた水面（平衡または一時停止の直後に雨を止めて測る。新しいパラメータ 1 つ） | 転送 0・描画は変わらない場合の下限で、アップロードと描画の最も明確な切り分け（`depthEvery=N` はその段階版）。`perfHook` はすでに `afterFirstJump` で降雨を始めているので、それを止めるパラメータ 1 つで足りる |
| `arrows=0` | 矢印は既定で表示され、Worker は最短 100 ms ごとに送り、メインは GeoJSON のソースを 10 Hz で `setData` する。MapLibre はタイルが最も多い p85 で矢印を並べ直す。05 では除外していない |
| 地形のみ（`water=0`） | 基準（05 では 59.6 fps、最遅 58.5） |
| vsync を外す起動の引数 | 効けば、天井に張り付いた条件の余裕が読める（§4.2。未検証） |
| GPU の時間（使えれば） | CPU のタイマーは、ドライバが後回しにする `texSubImage2D` や描画を見られない。render CPU 0.416 ms と fps の落ちが両立するのはこのため |

- 結果は g2 と平均 fps の両方で読む
- 転送が主因だった場合の次の候補: 変わった行だけの転送、Float16 のテクスチャ、更新の間引き（§5.2）。描画が主因なら遠景の LOD（別の spec）
- 原因を数字つきで `docs/perf/` と本節に書く

### 5.2 安価な改善の候補（R06-4、M4）

M2・M3 の判定で基準を超えた項目だけを直す。どれも §1 の「安価」の条件（依存・Worker・エンジンとメッセージの形を変えない）を満たす形で行い、満たさなくなったら別の spec に回す。

| 候補 | 根拠 | 注意 |
|---|---|---|
| `elevationRgba`・`depressionRgba` を軽くする、または分割する | 最長ブロック 123 ms の主因（75 ms・10 ms）。1 セルごとに配列を作って `set` している | Worker に移すのは地形のメッセージに RGBA を足すことになり、安価の外 |
| 止まっている間は水深の canvas ソースの `pause()` を呼ぶ（動き出したら `play()`） | 毎秒 60 回・1 回 1.7〜2.0 ms | MapLibre の `CanvasSource` が既に持つ API（`maplibre-gl-dev.mjs` 4601〜4609）。`pause()` は `_playing` を false にし、`hasTransition()`（同 4672〜4673。`_playing` を返す）を false にして、`prepare()` の `texture.update`（同 4649。`resize \|\| this._playing` のときだけ呼ぶ）を止める。ソースを作り直す必要はない。3D では隠した canvas は転送されないが、`hasTransition()` を真に保つので再描画は残る |
| `flowVectors()` の配列を使い回す | 1000 m で 8.5 MB を最短 100 ms ごとに確保 | 戻り値が次の呼び出しで上書きされる約束になる。呼び出し元（Worker の 1 か所）とテストで確かめる。型は変えない |
| DEM1A の 404 を省く（範囲の段を手がかりに渡す）。待つ要求の無くなった取得を止める | 段 2・3 の地域で範囲の外の z17 のタイルごとに 404 | 止める方は安価に収まる場合だけ |
| 51 fps の転送側の改善（間引き・変わった行だけ・Float16） | §5.1 で転送が主因と分かった場合 | 描画が主因なら行わない |
| `ui` のチャンク（`TextField` → `OutlinedInput` と `FormControl`） | 160.0 KB / 150 KB（tech-spec §14.2、RB-1 の順序） | 見た目とアクセシビリティの E2E を保つ |

Worker のチャンクの `maplibre-gl-shared` の複製（約 130 KB）は、ビルドの設定で消せるかを M2 で調べ、安価でなければ記録に留める。
