## 1. 目的

tech-spec §6.2 の `SimulationEngine` を、純粋な TypeScript で実装する。地形の上に置いた水が高所から低所へ移動し、窪地に溜まり、水位が上がって越流し、領域外へ流出するまでを、質量を保存して計算する。

UI・Worker・描画にはつながない（04 でつなぐ）。すべてを Node 上のテストで検証する。

## 2. スコープ

### 含む

- `TsSimulationEngine`（エンジン本体）と `FlowSolver`（1 step の計算）
- 降雨の投入（正規化つき、R03-4）
- 境界と無効セルの扱い（R03-2）
- 濡れたセルに絞った走査（tech-spec §6.7 の Active Cells）
- 統計、越流イベント、平衡の検出、流れのベクトル
- 全セルを走査する比較用のモード（テストで使う）
- Node で動くベンチマークのスクリプト

### 含まない

- Worker との接続と再生のループ（04）、表示（04・05）、時間変化する降雨（R04-3）、浸透・蒸発など base-spec §2 で考慮しないもの

## 3. モデル

### 3.1 状態

| 記号 | 型 | 意味 |
|---|---|---|
| `Z` | `Float32Array` | 標高（地形。変化しない） |
| `M` | `Uint8Array` | 有効セルマスク |
| `W` | `Float64Array` | 水深（現在） |
| `W'` | `Float64Array` | 水深（次の step。Jacobi 方式の書き込み先） |
| `A` | 数値 | セル面積 `cellSizeM²` |

水面標高は `H = Z + W` とし、f64 で計算する（tech-spec §6.5）。

### 3.2 1 step の計算（R03-1）

全セルを同時に更新する Jacobi 方式とする。`W` を読み、`W'` に書く。

```
W' ← W（走査範囲のみ）
for 走査範囲の有効セル i（行優先の固定順）:
  if W_i = 0: continue
  for i の 8 近傍 j（固定順。範囲外・無効セルは §3.3 の仮想セル）:
    ΔH_ij = H_i − H_j
    g_ij = ΔH_ij > θ ? k · w_j · ΔH_ij : 0
      w_j = 1（上下左右）、1/√2（斜め）
      k = c / Σ_j w_j、c = 0.5
  G_i = Σ_j g_ij
  if G_i = 0: continue
  s = min(1, W_i / G_i)          ← 持っている水より多くは出さない
  f_ij = s · g_ij
  W'_i −= Σ_j f_ij
  for j: 有効セルなら W'_j += f_ij、仮想セルなら outflow += f_ij · A
W ↔ W'（入れ替え）
```

- **流量は水面差に比例する**（base-spec §16 の「flow ∝ ΔH」）。次の step の水面標高は、自セルと近傍の水面標高の凸結合（重みが非負で和が 1）になる。流出側・流入側の係数の和は `k·Σw = c` 以下で、`s ≤ 1` と θ による打ち切りは係数を小さくするだけなので、`c ≤ 1` なら、どのセルも近傍の最高値を超えず最低値を下回らない（陽的な拡散の最大値原理）。`c = 1` でも凸結合にはなるが、自セルの係数が 0 になりうるので、Jacobi 方式に特有の市松模様の振動が減衰しない。そこで `c = 0.5` とする
- **水の量で上限を掛ける**ので、乾いた斜面（`W = 0`）からは流れ出さず、`W` は負にならない
- 薄い水が急な斜面にあるときは、`s` によって持っている水のすべてが 1 step で下へ移る。水は斜面を 1 step に 1 セルずつ下る
- すべての水が出ていく場合（`s < 1`）は、最後の流量を `W_i − (それまでの合計)` とし、`W'_i` がちょうど 0 になるようにする。丸め誤差で微小な水が残り続けるのを防ぐため
- 質量は、流出元から引いた量をそのまま流入先か `outflow` に足すので、構成上保存される（誤差は f64 の丸めのみ）
- 下り先が1つしかないセルでも、1 step に動くのは水面差の `k·w` 倍（上下左右の近傍なら約 7.3%）にとどまる。下り先の重みの和で正規化すれば速くなるが、受け手側の係数の和を抑える証明が複雑になるので、PoC では採らない。これが §4 の遅さの一因である

### 3.3 境界と無効セル（R03-2）

グリッドの外の近傍と無効セルは、**標高が流出元セルと同じで、水深 0 の仮想セル**として扱う。仮想セルへの流量は `outflow`（領域外流出）に数える（base-spec §18、tech-spec §7.2）。

- この扱いでは、端のセルと無効セルに接するセルの水は、水深が θ を超える限り外へ出る
- 02 の Priority-Flood が端と無効セルを起点にしているのと一致するため、十分な水を入れて平衡させた水面は、02 の満水時の水面 `F` と（θ の範囲で）一致する。これを検証の基準に使う（§6）

### 3.4 流れの閾値 θ（R03-3）

`θ = 1e-5 m`（tech-spec §6.6 の epsilon と同じ値）とする。

水面差が θ 以下の近傍には流さないので、平衡状態でも、池の水面は 1 セルあたり最大 θ まで傾いたまま止まりうる。その傾きは池の幅に比例して積み上がる。θ = 1e-5 m なら、512 セル幅でも 5mm 程度に収まり、水面標高の誤差 1cm 以内（tech-spec §6.6）を満たす。

### 3.5 走査範囲（Active Cells）

- 水が流れ出すのは濡れたセル（`W > 0`）だけなので、**濡れたセルの外接矩形**の中だけを走査する。流入先になりうる周囲 1 セルも含める
- 外接矩形は各 step の終わりに更新する。行優先の固定順で走査するので、結果は決定的である
- **不変条件: 走査範囲の外では、`W` と `W'` の両方が 0 である。** 範囲が縮むときは、外れた部分を両方のバッファで 0 にする。これを怠ると、入れ替えの後に `W'` に残っていた古い値が現れ、質量保存が崩れる
- 水が中心から四方に広がると、外接矩形は範囲全体に近づく（512² セル × 8 近傍で約 200 万回の計算／step となり、tech-spec §6.3 の基準の境目）。その場合の改善として、16 × 16 セルのブロックごとに「濡れているか」の印を持つ方式を、06 の比較対象にする。固定順で走査すれば決定性は保たれ、上の不変条件もそのまま使える
- テスト用に、全セルを走査するモード（`scanMode: 'full'`）を持つ。濡れていないセルは何もしないので、両モードの結果はビット単位で一致するはずである

tech-spec §22〜§23 の `Set<number>` による管理は採らない。外接矩形のほうが単純で、走査順も自然に決まる。性能が足りなければ 06 で見直す。

### 3.6 降雨の投入（R03-4）

`addRainfall({ x, y, radiusM, amountMm })`（座標はグリッドの北西端からの m）について:

1. セルの中心が円内にあるセルの集合を `C` とする。`C` は、円の外接矩形をグリッドで切らずに走査して数える（グリッドの外のセルと無効セルを含む）
2. `C` のうち、グリッドの中にある有効セルの集合を `S` とする
3. `C` が空（半径がセルより小さい）なら、`(x, y)` を含むセルが有効であればそれ1つを `C = S` とする。無効（またはグリッドの外）なら「降雨中心に標高データがありません」というエラーにする
4. `S` が空なら同じエラーにする
5. 投入総量 `V = π · radiusM² · amountMm / 1000 × |S| / |C|`（m³）
6. `S` の各セルに、水深 `V / (|S| · A)` を足す（`= π · radiusM² · amountMm / 1000 / (|C| · A)`。`|C| · A ≈ πr²` なので、ほぼ雨量そのもの）
7. `totalWater += V`

円がすべて有効セルなら `|S| = |C|` で、投入総量は、セルの大きさによらず πr² × 雨量に厳密に一致する（tech-spec §20 #5、R03-4）。円が範囲の端や無効セルで切れるときは、切れた部分に降るはずだった雨を投入しない。各セルの水深は、円がすべて有効な場合と同じになる（R04-8。2026-09-11 に改訂。改訂の前は `V` を `S` に集中させていたので、切れた円では残りの有効セルに水が集まった）。雨の降る範囲の形はセルの格子による近似になる。

### 3.7 越流イベント（R03-6）

- `setDepressions(list: { id, pitIndex, spillElevation }[])` で、02 の地形解析が求めた窪地（R02-3 の閾値を満たすもの）を受け取る。エンジンは地理情報も窪地のラベルも持たず、最低点のセル番号と spill 標高だけを知る
- 各 step の終わりに、まだ通知していない窪地について `H[pitIndex] ≥ spillElevation − 0.01` を調べ、満たしたら `{ type: 'spill', step, depressionId, spillElevation }` を `StepStats.events` に入れる
- 通知は窪地ごとに1回とし、`reset()` で通知済みの記録を消す
- 判定を「池の最低点の水位」で行うのは、雨が窪地の縁のセルに直接落ちたときに、局所的に水が縁を越える瞬間を「越流の始まり」と誤判定しないためである

### 3.8 統計と平衡

各 step の終わりに `StepStats` を返す。

| 項目 | 内容 |
|---|---|
| `step` | 実行済みの step 数 |
| `totalWater` | 累積の投入水量（m³） |
| `storedWater` | `Σ W × A`（m³） |
| `outflowWater` | 累積の領域外流出量（m³） |
| `maxDepth` | 最大水深（m） |
| `floodedArea` | 水深 1cm 以上のセルの面積（m²） |
| `settled` | この step で、θ を超える水面差による流れが1つも無かった |
| `massError` | `totalWater − storedWater − outflowWater`（m³）。開発用の表示と 06 の計測に使う |
| `events` | この step で起きた越流イベント |

初期水量は 0（`loadTerrain` と `reset` で水を消す）なので、質量保存の式は `totalWater = storedWater + outflowWater` になる。

### 3.9 流れのベクトル

`flowVectors(): { x: Float32Array; y: Float32Array }` は、現在の状態に §3.2 の式を当てはめたときの各セルの流出を、流出先の方向の単位ベクトルで重み付けして足したもの（水深の単位 m／step）を返す。濡れていないセルは 0。

step のたびに計算するのは無駄なので、**呼ばれたときに現在の状態から計算する**（水を動かさずに §3.2 の式を評価する。走査範囲を1回なめる程度の負担）。04 は、矢印が表示されていて、かつ frame を送る tick でだけ呼び、間引いて水の流れの矢印にする。

## 4. 既知の性質と限界

### 4.1 大きな池の水面が平らになるまでに時間がかかる

流量が水面差に比例する陽的な方式は、拡散方程式と同じ性質を持つ。水が斜面を下って窪地に集まるまでは速いが、池の最後の平らならしは遅い。

レビュー役の見積もり（2026-09-10）を記す。有効な拡散係数は約 0.18 セル²／step で、幅 L セルの池の凹凸が消える時定数は約 `L² / 1.75` step になる。水面の凹凸（初期 50cm 程度）が 1cm 以内に収まるまでに約 4 時定数、θ = 1e-5 m で `settled` になるまでに約 9 時定数かかる。

| 池の幅 L | 1cm 以内まで | `settled` まで | 1x（毎秒 60 step）での時間 |
|---|---|---|---|
| 30 セル | 約 2,000 step | 約 4,700 step | 35〜80 秒 |
| 100 セル | 約 23,000 step | 約 52,000 step | 6〜15 分 |
| 512 セル | — | — | 数時間 |

- 半径 10m・100mm（31m³）の降雨でできる池は幅 20 セル未満の見込みで、60 秒以内に収まる
- 半径 100m・100mm（3,141m³）の降雨は、深さ 0.3m なら約 1 万 m²、幅 100 セル規模の池になり、平衡まで数分〜十数分かかる見込み

平衡までの時間を決めるのは、降雨の半径ではなく、できる池の幅である。

**対策の方針:** 06 で平衡までの時間を計測する（R06-3）。目標に届かなければ、次のどちらかを別の spec として起こす。`SimulationEngine` のインターフェースは変えずに差し替えられる。

1. **本命: (b) 静的な fill-spill-merge 法**（Barnes ほか, 2020）。与えた水量に対する平衡の状態を直接求める。02 の Priority-Flood の構造を流用できる
2. 次点: (a) 運動量を持つ virtual pipe モデル。水面差が波として伝わり、L に比例する時間で平らになる

それまでの最も安価な緩和策は、04 の「最速」の再生（R04-5）である。

### 4.2 入れ子の窪地の越流は通知されない

02 の Priority-Flood が求める満水時の水面 `F` は、最も外側の spill 標高で決まる。そのため、大きな窪地の中にある小さな窪地は単独の窪地として扱われず、1つのラベルにまとめられる。越流イベント（§3.7）は外側の池が満ちたときにしか出ず、内側の小さな窪地から外側の池へ溢れる瞬間は通知されない。

PoC ではこれを許容する。将来は、窪地の階層構造（Barnes ほか, 2020）で扱える。

## 6. テスト

### 6.1 base-spec §47 の 4 ケースと平衡水位（tech-spec §11.2）

| ケース | 検証内容 |
|---|---|
| 平面 | 平らな底を持ち、周囲を高い縁で囲んだ盆地に置いた水が広がり、平衡後に水面標高の最大と最小の差が 1cm 以内。境界からは排水されるので、縁の無い平面では水がすべて流出してしまい検証にならない |
| 傾斜面 | 水は下り方向にしか動かない。置いた位置より高いセルは水を得ない。水の重心が下り方向へ移る |
| 単純窪地 | 窪地の外に置いた水が窪地に集まり、平衡後の水面が 1cm 以内で平ら |
| 越流 | 峠でつながった2つの窪地の一方に、その容量を超える水を置くと、もう一方が水を得る。一方の窪地について越流イベントが1回だけ出る |
| 平衡水位 | 周囲より高い縁に囲まれた窪地に体積 V の水を入れ、平衡後の水面標高が、V と地形から二分法で求めた理論値と 1cm 以内で一致する |
| 満水との一致 | 十分な水を入れて平衡させた水面が、02 の `analyzeDepressions` の `F` と一致する（有効なセルで F − 1e-9 ≤ H ≤ F + θ × (d(i) + 2) + 1e-9。d(i) は、窪地の成分ごとに、成分の外の同じ標高の隣（流出口）に接する成分内のセルを起点に BFS した距離。+2 は、流出口から池への 1 ホップと、グリッドの端・無効セルに接する流出口に残る θ 以下の水の分（仮想セルは同じ標高なので、水面差がその流出口の水深になり、θ 以下で流れが止まる）。下限は、水面が低すぎる不具合（降雨の正規化や境界の流出の誤り）を捕まえる） |

### 6.2 性質のテスト（fast-check）

地形は、平坦・斜面・複数の窪地・ランダムな凹凸・無効セルの混在を生成する。降雨は 1〜3 回、step は 1〜200 回とする。

| 性質 | 内容 |
|---|---|
| 質量保存 | 各 step で `|massError| ≤ totalWater × 1e-9`（tech-spec §11.3） |
| 非負 | すべての step で `W ≥ 0` |
| 局所的な最大値原理 | 任意の地形で、各有効セル i の次の水面標高 `H'_i` が、i 自身と 8 近傍の現在の `H`（仮想セルは §3.3 の定義）の最小値以上・最大値以下に入る。§3.2 の凸結合がそのまま性質になる |
| 決定性 | 同じ入力を2回実行すると、`W` がビット単位で一致する |
| 走査範囲 | `scanMode: 'bbox'` と `'full'` の `W` がビット単位で一致する |

### 6.3 個別のテスト

| 対象 | 内容 |
|---|---|
| 降雨の正規化 | セルの大きさ 0.98m・3.9m・7.8m、半径 1m・10m・100m のすべてで、投入量が πr² × 雨量と相対 1e-12 以内で一致。半径がセルより小さいときは 1 セル。無効セルには入れない。中心が無効セルならエラー。円が範囲の端・無効セルで切れる場合、投入量は円内の有効セルの割合（`|S| / |C|`）に減り、各セルの水深は円がすべて有効な場合と同じ（R04-8） |

| R03-1 | 流量の式 | §3.2 のとおり | base-spec §16 の「水面差に比例」をそのまま式にし、陽的な拡散の最大値原理で振動しないことを保証する。レビュー役の案（1 step の流出を水面差の半分までに制限）は、周囲 8 セルから同時に水を受けるセルが隣より高くなりうる（Jacobi 方式では、受け手が複数の送り手から同時に受け取るため）。係数で上限を掛けるほうが、安定であることを示しやすい |
| R03-2 | 境界と無効セル | 仮想セルの標高を流出元セルと同じにする（レビュー役の案を採る） | 02 の Priority-Flood と平衡状態が一致し、検証の基準が得られる。境界の外の地形を外挿する方法は物理的には自然だが、この一致が崩れる |
| R03-3 | 流れの閾値 θ | 1e-5 m | レビュー役の案（1mm）では、池の水面が 1 セルあたり 1mm まで傾いたまま止まりうるため、100 セル幅の池で 10cm の傾きが残り、1cm の精度目標を守れない |
| R03-4 | 降雨量の正規化 | §3.6 のとおり（レビュー役の案を採る） | 統計に出る投入水量が、DEM の解像度によらず理論値と一致する |
| R03-5 | 静的な平衡計算 | 別アルゴリズムを持たず、動的モデルを収束まで回して得る | 実装を1本に絞れる。ただし §4 のとおり、大きな池では平衡まで時間がかかる。06 の計測（R06-3）で目標に届かなければ、§4 の (a) か (b) を別の spec で追加する。base-spec §55 の Phase 2（水の平衡計算）との差異になる |
| R03-6 | 越流イベントの判定 | §3.7 のとおり | 局所的な越流を誤判定しない。エンジンに地理情報や窪地のラベルを持たせずに済む |
| R03-7 | インターフェースの追加 | §3.10 のとおり | 越流イベント（base-spec §21）、平衡での自動停止（R04-5）、水の流れの矢印（base-spec §32）、質量誤差の表示（06）に必要 |
