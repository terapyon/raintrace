### 1.1 調べて分かったこと（`feat/08-physical-time` の `ba9cc26` の時点。行番号はすべてこの時点で確かめた）

- **流れの式は無次元である。** 8 近傍へ `g = k·w·ΔH`（`k = c / (4 + 4/√2)`、`c = 0.5`）を流し、θ = 1e-5 m 以下の水面差には流さない（`src/simulation/FlowSolver.ts:10-24`・`117-118`・`150-151`、`src/simulation/constants.ts:14-18`）。セルの大きさも重力も摩擦も式に入っておらず、1 step が何秒に当たるかは決まらない
- **境界と無効セルは仮想セル**（流出元と同じ標高・水深 0）で、そこへの流量を流出に数える（`FlowSolver.ts:105-116`・`142-149`・`188`・`208`）
- **持っている水より多くは出さず、最後の近傍に残りを渡して 0 にする**（`FlowSolver.ts:193-210`）。質量は構成上保存される
- **走査範囲は濡れたセルの外接矩形と周囲 1 セル**で、「水は 1 step に 8 近傍（周囲 1 セル）までしか動かない」ことに依っている（`src/simulation/WaterGrid.ts:78-86` の `endStep` の説明）
- **雨は開始のときに 1 回だけ置く。** Worker の `start` が `engine.addRainfall(rain)` を 1 回呼ぶ（`src/workers/simulationRunner.ts:153`）。エンジンは円内の有効セルに水深を足し（`src/simulation/TsSimulationEngine.ts:83-89`）、円が切れるときは投入量を R04-8 の割合で減らす（`src/simulation/Rainfall.ts:96-100`）
- **平衡は「θ を超える流れが 1 つも無い」**（`TsSimulationEngine.ts:107` の `settled: !flow.flowed`）で、スケジューラがそこで自動停止する（`src/workers/playbackScheduler.ts:132-136`）
- **速度は 1 tick の step 数の上限**（1x = 毎秒 60 step）で、「最速」は 12 ms の時間予算だけで回す（`playbackScheduler.ts:4-6`・`149-156`、`src/shared/protocol.ts:12`、`src/ui/components/PlaybackControls.tsx:9`）
- **窪地解析（Priority-Flood）は 8 近傍**（`src/simulation/terrain/analyzeDepressions.ts:70` の起点の判定、`83` の走査）。近傍の表は D8 の流向と共有している（`src/simulation/terrain/neighbors.ts:7-8`、`d8FlowDirection.ts:1`）。越流イベントの窪地（`simulationRunner.ts:91`）、窪地の塗りと ○（あふれ出し点）、07 の印の説明の数値（`spillElevation`・`maxDepthM`・`capacityM3`・`areaM2`、`analyzeDepressions.ts:141-152`）、`fillMatch.test.ts` の基準は、すべてこれを使う
- **矢印は大きさを表示に使っていない。** 0 かどうかだけを見て、方位だけを地図に渡す（`src/workers/flowArrows.ts:22-23`、`src/map/waterFeatures.ts:16`）。大きさの単位は「m／step」と書かれている（`FlowSolver.ts:216`・`224`、`flowArrows.ts:3`、`protocol.ts:85`）
- **03 の性質のテストの「局所的な最大値原理」**（`src/simulation/properties.test.ts:195`）は、局所慣性式では成り立たない（水面差が波として伝わり、一時的に周りの水面を越える）。scenarios の「傾斜面: 置いた位置より高いセルは水を得ない」（`src/simulation/scenarios.test.ts:31`）も、慣性で破れうる
- **06 の実測**（開発機、tech-spec §14.1 の `specs/tech-spec.md:1252-1258`）: 1 step の中央値は 500 m・全面を濡らす雨で 6.50〜7.90 ms（Task 25 の `until=settle`。最悪は綾瀬の 7.90 ms）、1000 m で 30.80〜36.00 ms（参考）。平衡までは綾瀬 500 m・半径 10 m で 76.8 s（267,379 step。1 step 約 0.29 ms）

## 3. モデル

### 3.1 状態

| 記号 | 型 | 意味 |
|---|---|---|
| `Z` | `Float32Array`（N） | 標高（変化しない） |
| `M` | `Uint8Array`（N） | 有効セルマスク |
| `h` | `Float64Array`（N）× 2 | 水深（現在と次。Jacobi 方式） |
| `qx` | `Float64Array`（(W+1) × H） | 東西の面の単位幅流量（m²/s。東向きが正）。グリッドの西端・東端の面を含む |
| `qy` | `Float64Array`（W × (H+1)） | 南北の面の単位幅流量（m²/s。南向きが正）。北端・南端の面を含む |
| `t` | 数値 | 経過時間（s）。降雨の開始が 0 |
| `Δx` | 数値 | セルの一辺 `cellSizeM` |

水面標高は `η = Z + h`（f64）とする。流量は面（セルとセルの境）に置く（staggered grid）。

### 3.2 1 step の計算（局所慣性式。Bates, Horritt & Fewtrell 2010）

浅水方程式から移流項を落とし、摩擦を半陰的に扱う式である。LISFLOOD-FP の既定の解法として、都市の浸水の計算で広く使われている。

```
dt ← §3.3
for 走査範囲の中の各面 f（i と j の境。行優先の固定順）:
  η_i = Z_i + h_i、η_j = Z_j + h_j（仮想セルは §3.6）
  h_f = max(η_i, η_j) − max(Z_i, Z_j)          ← 面を通れる水の深さ
  if h_f ≤ H_DRY: q_f ← 0; continue
  S = (η_j − η_i) / Δx
  q̄_f = θ · q_f + (1 − θ)/2 · (q_前 + q_後)      ← θ 重み付け（下の説明。M0 で採用）
  q_f ← (q̄_f − g · h_f · dt · S) / (1 + g · dt · n² · |q_f| / h_f^(7/3))
  |q_f| ← min(|q_f|, FR_MAX · h_f · √(g · h_f))  ← フルード数の上限（§3.5）
正値の制限（§3.5）: 各セルの流出の合計が h_i · Δx / dt を超えるなら、そのセルから出る面の q を縮める
for 走査範囲の各有効セル i:
  h'_i = h_i + dt · (q_西 − q_東 + q_北 − q_南) / Δx + (降雨 §4.2)
t ← t + dt
```

- `g = 9.81 m/s²`、`n` は Manning の粗度係数（R08-3 で 0.03 に固定）
- 右辺の `q_f` は前の step の値（運動量を持つ）。これが 03 の拡散式との本質的な違いで、水面差が重力波として `√(g·h)` の速さで伝わるので、大きな池が平らになるまでの時間は池の幅 L に比例する（03 §4.1 の L² ではない）
- 面の流量は、一方のセルから引いた量をそのまま他方に足すので、質量は構成上保存される（誤差は f64 の丸めのみ。03 §3.2 と同じ）
- `h_f^(7/3)` は `h_f² · Math.cbrt(h_f)` で求める（`Math.pow` を避ける。§7.1）
- **de Almeida ほか（2012）の θ 重み付けを使う（`THETA = 0.8`。M0 で決めた。§12.1 の U2）**。上の式の右辺の運動量の `q_f` を、同じ向きに並ぶ両隣の面（東西の面なら西と東、南北の面なら北と南）の前の step の流量との加重平均 `θ·q_f + (1 − θ)/2 · (q_前 + q_後)` に置き換える。摩擦の分母の `|q_f|` は置き換えない（前の step のその面の値）。両隣の値は、この step で更新する前の値を使う（行優先でその場で更新するなら、西隣の面の古い値と、北の行の南北の面の古い値を取っておく。試作は `scripts/proto-08/li.ts`）。隣の面がグリッドの外にある（グリッドの端の面）ときは、その面の代わりに `q_f` 自身を使う。走査範囲の外の隣の面は §3.8 の不変条件で 0 なので、そのまま 0 を使う（`scanMode: 'full'` との一致を保つ）。`θ = 1` なら Bates 2010 と同じ式になる
- M0 の試作では、`θ = 1`（Bates 2010 のまま）は、斜面の上から一度に流れ込んで満ちた窪地（深さ 0.3 m、長さ 40 m）で市松（2Δx）の振動が育ち、20 分ほどで窪地の最低点の水面が spill 標高の ±30 cm で揺れ続けるようになった（面の流速 1〜1.7 m/s。`α` を 0.5 に下げても、フルード数の上限を外しても育つ）。平らな池（深さ 0.05〜2 m）でも、2Δx の成分が水深の約 1e-3 の大きさで残り、減らなかった。`θ = 0.8` なら育たない。ただし `θ < 1` は 2 次元では `α` を下げないと発散する（§3.3。`θ = 0.8` では `α = 0.6` は安定、`0.65` と `0.7` は発散）
- 平らな池の静振も `θ = 0.8` で速く収まる（62 × 62・水深 0.5 m に高さ 5 cm の山: 面の流速の最大が 1 cm/s を下回るまで `θ = 1` では 1 時間 47 分、`θ = 0.8`・`α = 0.5` では 1 分 36 秒。§12.1）

### 3.3 時間刻み

```
dt = min(DT_MAX, α · Δx / max(√(g · h_max), u_max))
```

- **`α = 0.5`（M0 で 0.7 から下げた。§12.1 の U1・U2）**。Bates ほか 2010 は Eq. (14) で `α` を「0.2〜0.7 の範囲の係数」としている（0.7 はその上限。LISFLOOD-FP 8.0 の ACC ソルバーの既定の Courant 数も 0.7。Shaw ほか 2021 の §2.3）。ただし 2 次元の格子に θ 重み付け（§3.2）を入れると、試作では `α` の安定の上限がおよそ `√(θ/2)` に下がった（`θ = 0.7` で 0.55〜0.6、`0.8` で 0.6〜0.65、`0.9` で 0.65〜0.7 の間に境があった。`θ = 1` の 2 次元の上限 `1/√2 ≈ 0.71` と同じ形）。`θ = 0.8` の上限（0.6〜0.65）に 2 割ほどの余裕を取って 0.5 にした。step 数は 0.7 のときの 1.4 倍になる（§7.2）
- `h_max` は、この step の始めの状態の最大水深（前の step の `WaterGrid.endStep` が求めた値）。`u_max` は前の step の面の流速 `|q_f| / h_f` の最大
- `u_max` の項について: Bates 2010 の式は `√(g·h)` だけである。`FR_MAX = 1`（§3.5）のもとでは、前の step の面の流速は `|q_f| / h_f ≤ √(g · h_f)` に抑えられ、`h_f` はその時点の最大水深を超えないので、`u_max` が `√(g · h_max)` を上回るのは、前の step から最大水深が減った場合の小さな差だけである。項は、`FR_MAX` を変えたときの守りとして残す
- **`DT_MAX = 1 s`（M0 で決めた。§12.1 の U2。コーディネーターの裁定〈2026-09-29〉の候補 (1)）**。乾いた地形に雨が降り始める最初の step（`h_max = 0`）と、薄い水しかない状態で dt が大きくなりすぎないための上限。薄い水の間は dt がこの上限に張り付く（DEM1A・`α = 0.5` で dt が上限を下回るのは、`DT_MAX = 10 s` なら最大水深が約 0.24 mm を超えてから、2 s なら約 6 mm、1 s なら約 24 mm を超えてから）。そのため上限は、降り始めの表示の細かさを決める（レビュー 1 の R2）
- M0 の試作（綾瀬 500 m、100 mm/h × 1 時間、再生のスケジューラを 60 tick/秒で模した。§12.1 の U2）: 最初の実時間 10 秒に表示が変わる tick の数（1 秒あたり）は、半径 10 m の雨で、実時間（1 倍）が `DT_MAX` 10 s・2 s・1 s の順に 0.2・0.6・1.1、10 倍が 6.1・7.2・10.2、60 倍が 56・57・60。範囲全体の雨で、1 倍が 0.2・0.6・1.1、10 倍が 9.7・10.7・12.6、60 倍が 57・58・60。dt が上限に張り付くのは降り始めの 1〜2 分だけで（半径 10 m の雨でも 5 分で最大水深 5 cm・dt 0.69 s）、雨の終わりまでの step 数は 1 s にしても 2 s より 0.2〜0.4% 多いだけだった（半径 10 m 7,324 → 7,353、範囲全体 13,918 → 13,937）。そこで 1 s にする。池ができた後の dt は 0.3〜0.5 s なので、実時間の再生でも 1 秒に 2〜3 回表示が変わる
- 候補 (2)（倍率 60 倍以下のときだけ dt を目標の時刻で切る）と (3)（10 s のまま）は採らない
- **降雨の終わりで切る**: `t < T_rain < t + dt` なら `dt = T_rain − t` とし、その step の終わりで雨がちょうど終わるようにする（投入の総量が `強度 × 継続時間` に厳密に一致する。§4.2）
- dt の目安（`α = 0.5`。M0 で改めた）:

| DEM（Δx） | h_max 0.1 m | 0.3 m | 0.5 m | 1 m | 2 m |
|---|---|---|---|---|---|
| DEM1A（0.98 m） | 0.49 s | 0.29 s | 0.22 s | 0.16 s | 0.11 s |
| DEM5A（3.9 m） | 1.97 s | 1.14 s | 0.88 s | 0.62 s | 0.44 s |
| DEM10B（7.8 m） | 3.9 s | 2.3 s | 1.8 s | 1.2 s | 0.88 s |

- dt は範囲の中で**最も深い水**で決まる。深い池が 1 つでもあると、ほかの場所がどれだけ浅くても dt は小さくなる。これが step 数を決める（§7）

### 3.4 乾湿と閾値

- 面を通れる水の深さ `h_f` が `H_DRY = 1e-5 m` 以下なら、その面の流量を 0 にする。値は今の θ（R03-3）と同じにし、定数 `FLOW_THRESHOLD_M`（`constants.ts:15`）の意味を「水面差の閾値」から「面を通れる水深の閾値」に改め、名前を `DRY_DEPTH_M` に替える。`DEPTH_EPSILON_M`（`constants.ts:12`）の説明の「流れの閾値 θ と同じ値」も改める
- 斜面の上の水は、各セルに `H_DRY` 以下の膜を残して止まる。03 の θ は「水面差」の閾値だったので、池の水面が 1 セルあたり θ ずつ傾いたまま止まりえた（03 §3.4）。局所慣性式では池の水面は平らになり、その傾きは無くなる
- `h_f` の定義により、水の無い高いセルへは水が上らない（静水を保つ。well-balanced）。平らな水面は、底の凹凸によらず動かない
- `h_f^(7/3)` は `h_f = 1e-5 m` の桁で 1e-12 程度になり、摩擦の分母が極端に大きくなる（流量はほぼ 0 になるので安定側）。**M0 の試作で数値の問題は出なかった**（勾配 1%・10% の斜面と 3 m の段差に 100 mm/h × 10 分。NaN・∞・負の水深なし、dt の最小は 0.9〜1.3 s〈雨の終わりで切った step を除く〉、質量誤差 1e-13 m³ 以下。§12.1 の U3）。`DRY_DEPTH_M = 1e-5 m` のままにする。1e-4 m に上げても、雨の後に面の流速が 1 cm/s を下回るまでの時間は、勾配 1% の斜面では変わらず（どちらも 1 時間で下回らない）、残る膜が増えるだけだった

### 3.5 正値の保証と安定

- **正値の制限**: セル i から出る面の流量の合計 `out_i = dt · Σ max(0, 出る向きの q) / Δx` が `h_i` を超えるなら、i から出る面の q に `h_i / out_i` を掛ける。どの面も、出る向きのセルは 1 つだけなので、縮めても両側の増減は一致し、質量は保存される。縮めた q を次の step の q として持つ（運動量を合わせる）
- 03 §3.2 と同じく、すべての水が出ていくセルは、最後の面に `h_i − （それまでの合計）` を渡して `h'_i` をちょうど 0 にする（丸めで微小な水が残り続けるのを防ぐ。今の `FlowSolver.ts:193-210` と同じ考え方）
- **フルード数の上限**: `|q_f| ≤ FR_MAX · h_f · √(g · h_f)`、`FR_MAX = 1`。局所慣性式は移流項を落としているため、射流（フルード数 > 1）では不安定になりやすい。この限界を述べているのは Bates 2010 ではなく de Almeida & Bates（2013）で、LISFLOOD-FP 8.0 の論文（Shaw ほか 2021、§3.2.2）も、フルード数が約 1.5 になった所で ACC ソルバー（局所慣性式）に数値の振動が出たと報告している（M0 の U1 で原典を確かめて直した。Bates 2010 が述べるのは、Manning の n = 0.01 の摩擦の小さい所での不安定）。上限を掛ける実装の例として、Deltares の Wflow.jl の局所慣性式は `froude_limit`（既定で有効）でフルード数を 1 以下に抑える。DEM1A の市街地には擁壁や段差で標高が 1 セルに 1 m 以上変わる所があり、そこを落ちる薄い水が射流になる。上限を掛けると急な段差での流速が小さめになり、到達時間は遅めに出るが、PoC の目的（どこへ流れ、どこに溜まるか）には影響しない。上限は平衡の水面を変えない（止まった水には効かない）。**M0 の試作で、Manning の斜面のテスト（§9.3。勾配 0.01）の斜面の内側のフルード数の最大は 0.59 で、上限は効かなかった**（効いたのは下端のグリッドの端の面だけ。仮想セルとの面は水面の勾配が `h/Δx` と急なので、端の流出は常に限界流〈フルード数 1〉になる）。3 m の段差（300 mm/h × 30 分）では、1 step あたり約 21 面で上限が効き、NaN・負の水深は出なかった（§12.1 の U5）
- 急な段差・崖・ランダムな凹凸での安定（NaN が出ない、`h ≥ 0`、質量保存）を、性質のテストで確かめる（§9.2）

### 3.6 境界と無効セル（R03-2 を保つ）

グリッドの外と無効セルは、今と同じく**標高が流出元のセルと同じで水深 0 の仮想セル**とする（R03-2）。

- 有効セル i と仮想セルの面では `η_仮想 = Z_i` なので、`h_f = h_i`、`S = −h_i / Δx`。水は常に外向きに押される。仮想セルは水を持たないので、面の流量が内向きになったら 0 に切る
- 外向きの流量 × `Δx` × `dt` を `outflow` に数える（base-spec §18）
- この境界は「端のセルの水は、水深が `H_DRY` を超える限り外へ出る」という今の性質を保つ。07 §5.1 の「マスクのセルは水深 1 mm 以上なら必ず外へ流し、マスクの外のセルは流出しない」も、マスクが 4 近傍になることで引き続き成り立つ（1 mm は `H_DRY` を超える）。02 の Priority-Flood が端と無効セルを起点にしていることとの一致（03 §3.3）も保つ
- 比べた案: 限界水深の流出（`q = √g · h^(3/2)`）は自由落下の端として物理的だが、仮想セルとの流量より大きくなり、端の近くの池の水位が Priority-Flood の `F` と食い違う。等流の流出（端のセルの地形の勾配を使う。LISFLOOD-FP の FREE 境界）は、端の勾配が逆向きだと水が溜まる。どちらも PoC の利点が小さいので採らない

### 3.9 自動停止（R08-6）

03 の `settled`（θ を超える流れが 1 つも無い）は、局所慣性式では成り立たない。面の流量は漸近的に 0 に近づくだけで、ちょうど 0 にはならないからである。さらに、池の水面の小さな揺れ（静振）は、Manning の摩擦（流速の 2 乗に比例）では振幅が小さくなるほど減りにくく、厳しい閾値ではいつまでも止まらない。

そこで次のとおりにする。

- `settled` = **雨が終わっていて**、かつ、この step のすべての面の流速 `|q_f| / h_f` が `SETTLE_VELOCITY = 0.01 m/s` 未満、という状態が `SETTLE_HOLD = 300 秒`（シミュレーションの時間）続いた
- 雨が降っている間は `settled` にしない
- 上限: 雨が終わってから `SETTLE_CAP = 6 時間`（シミュレーションの時間）で止める。`StepStats.stopReason` に `'settled' | 'cap'` を載せ、画面の文言を分ける（§6.2）
- **続く時間 `SETTLE_HOLD` を置く理由（Task 8 のレビューで見つけた。2026-09-30）**: 1 step だけで判定すると、水を一度に置いたとき（継続時間 0 の雨・`setInitialWater`）に面の流量が 0 から動き出す初めの step で、水が流れ出すところなのに `settled` になった（壁で囲んだ 40 × 40・勾配 1e-3 と 1e-4 に深さ 5 cm: 1 step 目で settled、その後に流速は 1.3 cm/s・2.2 cm/s まで上がる）。止まった水が勾配 S で 1 cm/s に達するのに約 `0.01 / (g·S)` 秒かかる。さらに閉じた範囲の水は揺れて、面の流速の最大が 1 cm/s の前後を何度も行き来する（上の 40 × 40 で、1 cm/s 未満の谷が 7〜40 秒）。R08-6 の意味（水がまだ加速している・流れている間は止めない）を変えずにこれを避ける方法を 3 つ測った: (i) 面の加速度から「τ 秒のうちに 1 cm/s に届くか」を見込む方法は、揺れの谷（流速の最大の極小で加速度がほぼ 0）で止まり、その後に 1 cm/s を超えた。(iii) 置いてから一定の時間は止めない方法は、揺れの谷を避けられない。(ii) 条件が続いた時間で判定する方法を、斜面（勾配 1e-3〜1e-5、40 × 40 と 100 × 12・セル 2 m、深さ 5 cm と 20 cm）と閉じた盆地（雨と一度に置いた水）の 17 通りで測ると、30・60・120 秒ではどれかが止まった後に 1 cm/s に戻り、300 秒ではどれも戻らなかった（300 秒は、止まった水が勾配 3.4e-6 で 1 cm/s に届く時間でもある）。そこで (ii) の 300 秒にした。ただし、どのセルの水深も `DRY_DEPTH` 以下なら、どの面の `h_f` もそれ以下で流量は 0 のまま変わらない（厳密に止まっている）ので、続く時間を待たずに `settled` にする（水の無い地形は今までどおり 1 step 目で止まる）。停止の意味と文言、上限（雨がやんでから 6 時間）は変えない。閉じた盆地の停止は 300 秒ほど遅れる。実 DEM はもともと上限で止まるので変わらない（§12.1）
- 1 cm/s は「目で見て水がほぼ動かない」目安である。斜面の膜と、池の静振の残りは、この閾値の下に入る見込み。静振の減衰は線形化した粗い見積もりなので、M0 の試作で、止まるまでのシミュレーションの時間を確かめる（§12 の U2）
- **停止は平衡ではない**（レビュー 1 の M1）。緩い斜面には、1 cm/s 未満の速さで流れ続けている薄い水が残る。Manning の等流で流速が 1 cm/s になる水深は `h = (u · n / √S)^(3/2)` で、`n = 0.03` なら勾配 0.01 で 0.16 mm、0.001 で 0.92 mm、1e-4 で 5.2 mm（`n = 0.1` なら 1.0 mm・5.6 mm・32 mm）である。この水は停止の後も池へ流れ込み続けるはずなので、停止の時点の池の水位は満水の水面 `F` にまだ届いておらず、停止の後に来るはずだった越流の通知も出ない。PoC の「どこに溜まるか」を見る目的には足りるとし、どれだけ残るかを M0 で測る（§12 の U6）。テストの平衡は別の止め方で見る（§9.1）
- **M0 の結果（§13.2 の Q1。ユーザーの裁定 2026-09-30 で R08-6 のまま）**: 3 地点の実 DEM（500 m、100 mm/h × 1 時間、半径 10 m と 100 m）では、**上の条件（すべての面の流速 < 1 cm/s）は雨がやんでから 6 時間の上限の中で一度も満たされず、停止の理由はすべて `cap` になった**（みなとみらい・半径 10 m だけは雨の後 8 時間 55 分で満たした。§12.1 の U2・U6）。流速が下がりきらないのは、池の静振ではなく（θ 重み付けで数分で収まる）、次の 2 つの薄い水の流れである
  - 段差（DEM1A の市街地で 1 セルに数 cm 以上）の縁を越える膜は、水深によらずほぼ限界流（流速 `√(g·h_f)`）で落ちる。流量が小さくなっても流速は `(g·q)^(1/3)` でしか下がらず、1 cm/s を下回るには単位幅流量が約 1e-7 m²/s まで下がる必要がある
  - グリッドの端・無効セルに接するセルの膜は、仮想セルとの面で同じく限界流で流れ出る（§3.6）
  - 上の膜の流れは、緩い斜面に広く残る mm の水が池へ少しずつ流れ込むことで何時間も続く。綾瀬・半径 10 m では、雨の後 24 時間でも面の流速の最大は約 2 cm/s、池の外に 0.59 m³（投入の 1.9%）が残った。渋谷・半径 10 m では雨の後 6 時間の時点で池の外に 9.8 m³（31%）が残り、雨の後 12 時間 19 分に越流の通知がもう 1 回来た（6 時間の上限で止めると見逃す）
- **受け入れた帰結（ユーザーの裁定、2026-09-30。§13.2 の Q1 は (a)）**: 停止の条件は R08-6 のまま変えない。その結果、M0 の実測では 3 地点 × 半径 10 m・100 m の 6 通りすべてが、雨の後 6 時間の上限（`stopReason = 'cap'`）で止まった。「水の動きがほぼ止まりました」（`settled`）は、実 DEM ではほとんど出ない。渋谷・半径 10 m では、止めた後（雨の後 12 時間 19 分）に来るはずの越流の通知を 1 件見逃す。上限の時点で池の外に残る水は、半径 10 m で 0.03〜9.8 m³（投入 31.4 m³ の 0.1〜31%）、半径 100 m で 16.7〜119 m³（投入 3,142 m³ の 0.5〜3.8%）。上限で止まったときの文言は、流速が下がって止まったときと分ける（§6.2）

### 3.10 流れのベクトル

`flowVectors()` は、各セルの中心の流速（m/s）を返す。

```
u_i = (qx_西 + qx_東) / 2 / h_i、 v_i = (qy_北 + qy_南) / 2 / h_i（h_i > H_DRY のとき。それ以外は 0）
```

### 4.1 入力（R08-7）

| 項目 | 範囲 | 既定 | UI |
|---|---|---|---|
| 時間雨量 | 1〜300 mm/h（整数） | 100 | 入力欄とスライダー（今の雨量の欄を置き換える） |

- 既定の 100 mm/h・1 時間は、今の既定（100 mm）と同じ総量になる。雨が終わった時点の投入水量は、今と同じ 31.4 m³ になる（E2E が引き継げる）
- 上限の 300 mm/h は、日本の 1 時間降水量の観測記録（気象庁の歴代全国ランキングの 1 位は 153 mm。千葉県香取〈1999-10-27〉と長崎県長浦岳〈1982-07-23〉。M0 の U1 で確かめた）の 2 倍程度の余裕を持たせた値。継続時間の上限 6 時間と合わせて総量の上限は 1,800 mm で、今の上限 1,000 mm（R04-6）を上回る
- 継続時間を選択にするのは、入力の検証を無くし、キーボードでも選びやすくするため

### 4.2 投入

- `setRainfall(rain)` は雨を**登録するだけ**にする。各 step の終わりに、雨が降っている間（`t < T_rain`）だけ、雨のセルに `ρ · dt` を足す
- 円の雨のセルと割合は 03 §3.6・R04-8 のまま（`planRainfall` を使う）。各セルの水深の増える速さは、円がすべて有効な場合と同じにする

```
I   = 時間雨量 / 1000 / 3600                       （m/s）
ρ   = I · π r² / (|C| · A)                          （各セルの水深の増える速さ。|C|·A ≈ πr² なのでほぼ I）
1 step の投入量 = ρ · dt · |S| · A = I · dt · π r² · |S| / |C|
総量 = I · T_rain · π r² · |S| / |C|                （円がすべて有効なら I · T_rain · π r²）
```

- §3.3 のとおり、雨の終わりの step は dt を切るので、総量は上の式に（f64 の丸めの範囲で）一致する
- `durationS = 0` は「開始のときに一度に置く」（今の `addRainfall` と同じ）とする。UI からは選べない。テスト（満水との一致、平衡水位など）で使う
- 雨のセルは走査範囲に含める（今の `grid.include`）。登録のときに 1 回含めれば、降っている間は常に濡れているので範囲に残る

### 4.3 範囲全体の雨（R08-4）

「範囲全体に降らせる」がオンのときは、すべての有効セルに `I · dt` を足す（割合の補正は要らない。総量 = `I · T_rain · 有効セルの数 · A`）。

- 「1 時間に 100 mm の雨」を素直に表すのはこちらである。平らな盆地で 100 mm/h × 2 時間なら水深はちょうど 0.2 m になり、テスト（§9.3）にも使える
- ただし走査範囲が最初から範囲全体になり、06 の「全面を濡らす雨」と同じ最悪の形になる（§7）。そのため既定はオフにする
- 降雨マーカーは表示したままにする（範囲の中心であることは変わらない。R04-2）

### 4.4 排水の項（将来の口だけ。R08-10）

08 では入れない。入れるときの形だけを決めておく。

- 「排水能力 D mm/h」を 1 つ置き、各 step で濡れたセルから `min(h_i, D · dt)` を引く
- 引いた量は `drainedWater`（累積、m³）として統計に分けて出す。流出（範囲の外へ出た量）とは混ぜない（07 §10 の申し送り）
- 質量保存の式は `totalWater = storedWater + outflowWater + drainedWater` になる
- base-spec §2 は下水道・排水ポンプを考慮しないとしているので、入れるときは base-spec との差異として記録し、免責の文（`strings.ts` の `disclaimer.lines`）と 07 のツールチップの「下水道…は考えていません」も見直す

## 6. 再生と表示

### 6.1 再生速度（R08-5）

速度は**実時間の倍率**にする。「60 倍」なら、実時間の 1 秒でシミュレーションの 60 秒（1 分）を進める。

| 選択肢 | 意味 | 2 時間の雨を見る時間 |
|---|---|---|
| 実時間 | 1 倍 | 2 時間 |
| 10 倍 | 実時間 1 秒で 10 秒 | 12 分 |
| 60 倍（既定） | 実時間 1 秒で 1 分 | 2 分 |
| 600 倍 | 実時間 1 秒で 10 分 | 12 秒 |
| 最速 | 時間予算の中で回せるだけ回す（今の 'max' と同じ） | §7.2 |

- スケジューラ（`PlaybackScheduler`）の繰り越しを、step 数から時間に替える。tick ごとに「倍率 × 前の tick からの実時間の経過」を目標に足し、`t` が目標に届くまで step を回す。12 ms の時間予算で届かなければそこで打ち切り、届かなかった分は繰り越さない（今の「予算で届かなかった分は繰り越さない」と同じ。`playbackScheduler.ts:149`）
- 目標を少し越える（最大 1 step の dt）のは許す。dt を目標に合わせて切るのは雨の終わりだけにする（切ると dt が細かくなり、step 数が増える）
- 計算が追いつかないときは、実際の倍率を統計に出す（「実時間の 27 倍」）。追いつかないことそのものは誤りにしない
- 「1 step 進める」は、一時停止中に 1 step（その時の dt）進める。今と同じ
- 自動停止は `settled` と `cap` の両方で止める（今の `last.settled` の判定〈`playbackScheduler.ts:132-136`〉を `stopReason !== null` に替える）

- 自動停止（settled。`strings.ts:95` の `平衡に達しました（Step n）` を置き換える）: 「水の動きがほぼ止まりました（経過 3時間10分）」

- 越流の判定（R03-6: 窪地の最低点の水面標高が spill 標高 − 1 cm に達したら 1 回）は変えない。ただし局所慣性式では、窪地の外から波で流れ込む水が慣性で一時的に水面を押し上げ、満水より早く 1 回だけ通知が出うる（レビュー 1 の R4）。M0 の試作で、通知の時刻と満水の時刻を比べた（§12.1 の U2）。**判定は変えない（平均を取らない。M0 で決めた）**。雨で満ちる窪地（斜面から流れ込む合成の窪地に 1 時間の雨、3 地点の実 DEM）では、通知は最低点の水面が spill − 1 cm を最後に下回った時刻の 1 step（1 秒）以内で、通知の後に下回ることは無かった。早い通知が出たのは、試験用の「一度に置く水」が段差の上から波になって流れ込む場合だけで、容量の 1.2 倍の水で通知が満水より 1.5 分ほど早く、その後 30〜200 step ほど水位が spill − 1 cm を下回った（容量の 0.9 倍の水では通知は出なかった）。UI の雨は 10 分以上かけて降るので、この場合は受け入れる

### 6.3 入力の検証（R04-6 の改訂）

§4.1 の表のとおり。範囲外の時間雨量は入力欄にエラーを出し、開始を押せなくする（今と同じ扱い）。継続時間は選択なので検証は要らない。範囲全体の雨がオンのときは、半径の検証をしない。`AMOUNT_MM`（`persistedSettings.ts:16`）は `INTENSITY_MM_PER_H = { min: 1, max: 300 }` に替える。

### 6.4 URL と localStorage（R08-8）

**方針**: 古い雨の値（総量の `mm`・`amountMm`）は読み替えない。雨量だけを既定（100 mm/h × 1 時間、範囲全体オフ）に戻し、半径を含むそれ以外の設定は残す（R08-8、§13.1 の N1）。

#### URL（tech-spec §3.3。`src/state/urlState.ts`）

| パラメータ | 意味 | 無いとき・不正なとき |
|---|---|---|
| `mmh` | 時間雨量（mm/h）。1〜300 の整数 | 保存値（無ければ既定 100） |
| `dur` | 継続時間（分）。10・20・30・60・120・180・360 のどれか | 保存値（無ければ既定 60） |
| `all` | `1` なら範囲全体に降らせる、`0` なら円 | 保存値（無ければ既定のオフ） |
| `r` | 半径（今のまま） | 今のまま |
| `mm`（古い URL） | **読まない**（無いものとして扱う） | — |

- 書くのは `mmh`・`dur`・`all`・`r` で、今の `size`・`mm`・`r` と同じく地点があるときだけ書く（`urlState.ts:67-71`）。`all` はオフでも `0` を書く（共有した URL を開いた人の保存値で、円と範囲全体が入れ替わらないようにするため）
- `mm` は管理するキー（`urlState.ts:28` の `MANAGED_KEYS`）に残す。こうすると、古い URL を開いた後、最初に URL を書くときに `mm` が消える。読む側では使わない
- 古い `?mm=50` を開くと、雨は保存値になる。v0.2.0・07 の利用者と初めての利用者では、保存値の雨は既定なので、100 mm/h × 1 時間になる（読み替えた 50 mm/h × 1 時間にはならない。R08-8）
- 例: `/?lat=35.6812&lon=139.7671&z=17&size=500&mmh=100&dur=120&all=0&r=10`

#### localStorage（tech-spec §8.3。`src/state/persistedSettings.ts`）

```ts
interface PersistedSettings {
  schemaVersion: 2
  rainfall: {
    intensityMmPerH: number  // 既定 100。1〜300 の整数
    durationMin: 10 | 20 | 30 | 60 | 120 | 180 | 360   // 既定 60
    radiusM: number          // 既定 10
    wholeRange: boolean      // 既定 false
  }
  // area・display（showOutflowCells を含む）・map・disclaimerAcknowledgedAt は変えない
}
```

今の `parsePersistedSettings`（`persistedSettings.ts:102-145`）は、`schemaVersion` が 1 でないか、どれか 1 つの項目が欠けるか不正なら、保存値全体を捨てる（`null`）。07 は `showOutflowCells` の欠けだけを既定で補った（`persistedSettings.ts:112`）。そのまま `rainfall` の形を変えると、v0.2.0・07 の利用者は注意事項の了解（`disclaimerAcknowledgedAt`）・ベースマップ・テーマ・範囲などをすべて失う。そこで、読み方を次のとおりにする。

| 保存値 | 読み方 |
|---|---|
| `schemaVersion: 2` | 今と同じく、すべての項目を検証する。どれかが欠けるか不正なら全体を捨てる。`showOutflowCells` の欠けの補い（07）と、矢印の間隔 5 → 10（R06-11）は残す |
| `schemaVersion: 1`（v0.2.0 と 07） | **雨量（`rainfall.amountMm`）は読まず、`intensityMmPerH`・`durationMin`・`wholeRange` を既定（100・60・false）にする**（`amountMm` が欠けていても、範囲外でも、捨てる理由にしない）。**`rainfall.radiusM` は今の検証（R04-6。1 m 以上、範囲の半分以下。`isValidRadiusM`）を通れば残す**。`radiusM` を含め、雨量以外の項目は今と同じ規則で検証し、`showOutflowCells` の欠けは `true` で補い、矢印の間隔 5 は 10 に読む。雨量以外の項目（`radiusM` を含む）が欠けるか不正なら、今までどおり全体を捨てる |
| それ以外（`schemaVersion` が無い・3 以上など） | 全体を捨てる（今と同じ） |

- 保存するときは常に `schemaVersion: 2` の形で書く。v1 を読んだ後、最初に設定が変わったときに v2 に置き換わる
- **`schemaVersion` を 2 に上げる理由**: `rainfall` の形が互換でなく変わる（`amountMm` が無くなり、必須の項目が 3 つ増える）。版を上げておけば、「古い形なので雨だけ既定に戻す（v1）」と「新しい形なのに壊れているので全体を捨てる（v2）」を、項目の有無から推し量らずに分けられ、テストの場合分けもはっきりする。07 の `showOutflowCells` は任意の項目を足しただけで形が変わらなかったので 1 のままにしたが、今回はそれに当たらない。なお、上げても上げなくても、v0.2.0 のビルドは 08 の保存値を読めない（v2 は版の不一致、版を 1 のままにしても `amountMm` の欠けで捨てる）ので、版を上げることで失うものは無い
- **戻したときの扱い（ユーザーの裁定 N2、2026-09-29）**: 08 の後で v0.2.0・07 のビルドに戻すと、v2 の保存値は捨てられ、設定は既定に戻り、注意事項がもう一度出る。ユーザーはこれを受け入れた
- 半径（`radiusM`）は `rainfall` の中にあるが、雨量とは違って意味が変わらないので残す（ユーザーの裁定 N1、2026-09-29）。範囲の半分を超えるなど検証を通らない半径は、ほかの項目の不正と同じく全体を捨てる理由になる（今と同じ）
- tech-spec §8.3 の「バージョニング方針」に、`clampArrowSpacing`（R06-11）・`showOutflowCells`（07）と並ぶ例外として、「v1 → v2 は雨量（`amountMm`）だけを既定の時間雨量・継続時間に戻し、半径を含むそれ以外を残す（R08-8、N1）」を書く

## 7. 性能

### 7.1 1 step の所要時間

局所慣性式の 1 step は、セルごとに面 2 つ（東と南）の流量、正値の制限、水深の更新の 3 回の走査になる。今の式（濡れたセルごとに 8 近傍の候補）と比べ、面ごとに `Math.cbrt` と割り算が 1 回ずつ増え、配列が 2 つ（`qx`・`qy`）増える。近傍は 8 から 4 に減る。草案では今の 0.7〜2 倍と見込んだ。**M0 の試作では約 2.1〜2.3 倍だった**（§12.1 の U4。開発機、Node 24.19.0、綾瀬 500 m・516 × 516、全面が濡れた状態で 600 step の中央値。今のエンジン〈06 の全面を濡らす雨〉9.8〜10.4 ms、試作〈θ 重み付けあり〉は範囲全体の雨で 22.5〜23.0 ms、半径 250 m の雨で 20.7 ms。θ 重み付けなしでは 18.6〜20.1 ms）。試作は走査を 6 回に分けた素直な書き方で、`Math.cbrt` だけで 1 step に約 3.6 ms（2 方向 × 26.6 万面）かかる。M1 の Node のベンチマーク（`scripts/bench-engine.ts`）で測り直す。06 の実測（ブラウザ）の 500 m・全面を濡らす雨の中央値 6.50〜7.90 ms は、Node の今のエンジンの 9.8〜10.4 ms の 0.6〜0.8 倍なので、ブラウザでは 500 m・全面で 12〜19 ms 程度と見込む（20.7〜23.0 ms × 0.6〜0.8）

### 9.2 性質のテスト（fast-check。03 §6.2 の置き換え）

地形は、平坦・斜面・複数の窪地・ランダムな凹凸・無効セルの混在に、**1 セルで数 m 変わる段差（擁壁・崖）** を足す。雨は一度に置くものと、継続時間のあるもの（強さ・時間・範囲全体をランダム）。

| 性質 | 内容 |
|---|---|
| 質量保存 | 各 step で `|massError| ≤ totalWater × 1e-9`（tech-spec §11.3 のまま） |
| 非負・有限 | すべての step で `h ≥ 0`、`h`・`qx`・`qy` が有限（NaN・∞ が無い） |
| 静水の保存 | 任意の地形の上に静水を置き、雨なしで回すと、`h` が変わらない。03 の「局所的な最大値原理」（`properties.test.ts:195`）を置き換える。置く水と許容は下の (a)(b) のとおり |
| 時間刻み | 各 step で `dtS ≤ DT_MAX_S`、かつ `dtS ≤ α · Δx / √(g · h_max)`（前の step の h_max）。雨の終わりをまたぐ step は無い |
| 決定性 | 同じ入力を 2 回実行すると `h`・`qx`・`qy` がビット単位で一致 |
| 走査範囲 | `scanMode: 'bbox'` と `'full'` の結果がビット単位で一致 |
| 走査範囲の外 | 範囲の外の `h`・`qx`・`qy` が 0 |

静水の保存の置き方と許容（レビュー 1 の M2）:

- (a) 置く水は `h = max(0, min(η0, F₄) − Z)` とする（`η0` は任意の水面標高、`F₄` は 4 近傍の Priority-Flood の満水の水面）。「すべてのセルを `η0` まで満たす」と、端や無効セルにつながる所（`F = Z`）の水は外へ流れ出るので静水にならない。`F₄` で切れば、端につながる所は乾いたまま、それぞれの池はその spill 標高までで止まる
- (b) f64 の丸め: `Z + (η0 − Z)` は一般には `η0` に戻らない（Sterbenz の条件の外）。そのため面の水面差が 0 にならず、微小な流れが立ちうる。**`Z` と `η0` を二進の格子（`k / 256 m`）に載せて演算を厳密にし、`h` がビット単位で変わらないことを確かめる（M0 で決めた。§12.1 の U7）**。格子の上では、`|Z|`・`|η0|` が 2^15 m 未満なら、`Z`（Float32）・`η0 − Z`・`Z + h` がすべて丸めなしで表せる。試作では 200 試行（40 × 40、セル 0.97〜7.8 m、無効セルあり、池の水面が標高 0 をまたぐ場合を含む）×500 step で、格子に載せた場合も載せない場合もビット単位で変わらなかったが、載せない場合は保証が無いので採らない
